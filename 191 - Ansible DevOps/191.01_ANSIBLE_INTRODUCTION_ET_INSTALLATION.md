# 2. Pourquoi automatiser ?

Avec l’augmentation du nombre de serveurs, de services et d’environnements, les opérations manuelles deviennent rapidement coûteuses et difficiles à reproduire.

Une administration manuelle ressemble souvent à ceci :

```text
serveur 1 ── SSH ── installer paquet ── modifier config ── redémarrer service
serveur 2 ── SSH ── installer paquet ── modifier config ── redémarrer service
serveur 3 ── SSH ── installer paquet ── modifier config ── redémarrer service
...
```

Le même travail répété manuellement multiplie :

- le temps passé ;
- les différences entre machines ;
- les oublis ;
- les erreurs de saisie ;
- la difficulté à reproduire une configuration.

Ansible propose de décrire les opérations à automatiser puis de les appliquer de manière centralisée.

```text
                  ┌─────────────────────┐
                  │   CONTROL NODE      │
                  │      Ansible        │
                  └──────────┬──────────┘
                             │
                       SSH / automation
                             │
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼
        ┌─────────┐     ┌─────────┐     ┌─────────┐
        │ cible 1 │     │ cible 2 │     │ cible 3 │
        └─────────┘     └─────────┘     └─────────┘
```

---

# 3. Présentation générale d’Ansible

Le support DataScientest présente Ansible comme un outil d’automatisation open source utilisé notamment pour :

1. la **gestion de configuration** ;
2. le **déploiement d’applications** ;
3. l’**orchestration de services** ;
4. le **provisionnement de ressources**.

Dans le parcours du cours, Ansible communique principalement avec les machines distantes via **SSH** et ne nécessite pas l’installation d’un agent Ansible permanent sur chacune des cibles.

Les configurations et automatisations sont principalement décrites à l’aide de fichiers lisibles par l’humain, notamment YAML, avec l’usage de templates Jinja2 dans les chapitres suivants.

---

# 4. Les avantages mis en avant dans le cours

Le support d’origine met en avant les caractéristiques suivantes.

| Caractéristique | Idée principale |
|---|---|
| Open source | Ansible est disponible comme projet open source. |
| Sans agent | Pas d’agent Ansible permanent à déployer sur les machines Linux du TP. |
| Accessible | La syntaxe et les fichiers de configuration sont conçus pour rester lisibles. |
| Puissant | Des tâches simples jusqu’aux orchestrations plus complexes. |
| Flexible | Utilisable sur des environnements locaux, cloud, machines virtuelles et autres infrastructures. |
| Léger | Le modèle ne repose pas sur un service agent Ansible tournant en permanence sur chaque cible du TP. |

Le point important pour débuter est le suivant :

```text
Ansible ne remplace pas seulement une commande shell.
Il permet de décrire et d’orchestrer l’état attendu d’un ensemble de machines.
```

Les notions d’**idempotence**, de modules spécialisés et d’état souhaité seront approfondies dans le chapitre `191.02`.

# 5. Principaux cas d’usage

## 5.1 Gestion de configuration

Ansible permet d’appliquer une configuration sur plusieurs machines à partir d’un point central.

Exemple conceptuel :

```text
Inventaire
   │
   ├── serveur-a
   ├── serveur-b
   └── serveur-c
          │
          ▼
Playbook : "installer et configurer le service"
          │
          ▼
Configuration appliquée aux machines ciblées
```

---

## 5.2 Déploiement d’applications

Le support présente Ansible comme un moyen de décrire les étapes nécessaires au déploiement d’une application, puis de les exécuter sur les hôtes distants sans répéter les mêmes manipulations à la main.

Cette logique sera concrètement utilisée plus tard avec :

```text
playbooks
    ↓
rôles
    ↓
variables / templates
    ↓
application déployée
```

---

## 5.3 Orchestration

L’automatisation ne consiste pas seulement à effectuer une action sur une machine.

Un scénario peut devoir coordonner plusieurs composants :

```text
préparer le serveur
        ↓
installer les dépendances
        ↓
configurer le service
        ↓
déployer l’application
        ↓
redémarrer si nécessaire
        ↓
valider
```

Les playbooks et rôles fourniront cette structure dans les chapitres suivants.

---

## 5.4 Provisionnement

Le support original rappelle qu’Ansible peut également interagir avec des plateformes cloud et des ressources d’infrastructure.

Dans ce dépôt, le cursus Terraform est toutefois traité séparément sous `192 - Terraform DevOps/`.

Pour le parcours pratique Ansible, l’infrastructure initiale est volontairement créée avec **Multipass**, puis Ansible est utilisé pour automatiser les machines obtenues.

# 7. Architecture conceptuelle d’Ansible

Le support de cours introduit plusieurs briques importantes.

```text
                         ANSIBLE
                            │
         ┌──────────────────┼───────────────────┐
         │                  │                   │
         ▼                  ▼                   ▼
     Inventory           Playbooks           Modules
         │                  │                   │
         │                  └──── Tasks ─────────┘
         │
         ├──── Hosts / Groups
         │
         └──── Variables

      + Plugins
      + Cloud / réseau
      + autres intégrations
```

## 7.1 Modules

Les modules sont les unités fonctionnelles utilisées par Ansible pour réaliser des actions : gérer des paquets, fichiers, services, utilisateurs, etc.

Ils seront étudiés dans :

```text
191.02_ANSIBLE_MODULES_ET_COMMANDES_AD_HOC.md
```

---

## 7.2 Playbooks

Les playbooks sont des fichiers YAML décrivant des séquences d’actions appliquées à des hôtes ou groupes d’hôtes.

Ils constituent le cœur de l’automatisation déclarée dans le cours.

```text
playbook
   │
   ├── play 1
   │    ├── task
   │    └── task
   │
   └── play 2
        ├── task
        └── task
```

Ils seront détaillés dans `191.04`.

---

## 7.3 Inventaires

L’inventaire indique à Ansible **quelles machines** il doit gérer et comment les organiser.

```text
inventory
├── dev
│   └── host-a
├── test
│   └── host-b
└── prod
    └── host-c
```

Les inventaires seront étudiés dans `191.03`.

À ce stade, il suffit de retenir qu’ils participent à l’extensibilité de l’outil.

# 9. Création rapide des machines Multipass

Le guide enrichi utilise un fichier cloud-init `config.yaml` puis crée quatre VMs Ubuntu 24.04.

Depuis la machine physique :

```bash
multipass launch 24.04 --name ansible-master --cloud-init config.yaml
multipass launch 24.04 --name cible1 --cloud-init config.yaml
multipass launch 24.04 --name cible2 --cloud-init config.yaml
multipass launch 24.04 --name cible3 --cloud-init config.yaml
```

Vérification :

```bash
multipass list
```

Puis :

```bash
multipass info ansible-master
multipass info cible1
multipass info cible2
multipass info cible3
```

> Les adresses IP affichées dans les supports sont des exemples observés lors d’une exécution. Elles ne doivent pas être copiées aveuglément : utilisez celles retournées par votre propre `multipass list`.

# 10. Installation d’Ansible sur Ubuntu

Le support présente deux voies principales :

```text
Installation Ansible
      │
      ├── apt     → voie simple du cours
      │
      └── pip     → variante Python présentée à titre informatif
```

Toutes les commandes suivantes doivent être exécutées sur le **control node** `ansible-master`, et non sur les trois cibles.

---

## 10.1 Installation via `apt`

Le support propose :

```bash
sudo apt-add-repository --yes --update ppa:ansible/ansible
sudo apt-get install ansible
```

Puis :

```bash
which ansible
ansible --version
```

Le résultat attendu est que :

1. le binaire `ansible` soit trouvé dans le `PATH` ;
2. `ansible --version` s’exécute correctement ;
3. la commande indique le fichier de configuration actuellement chargé.

Les numéros de version affichés dans le support original sont des exemples issus de l’environnement de cours. La vérification pertinente sur une installation donnée reste donc :

```bash
ansible --version
```

---

## 10.2 Installation via Python / `pip`

Le support présente également une installation Python à titre informatif :

```bash
which pip3
sudo apt install -y python3-pip
pip3 install ansible
```

Puis :

```bash
which ansible
ansible --version
```

L’objectif pédagogique de cette variante est également de comprendre le rôle de `PATH` : lorsqu’une commande est exécutée, le système recherche l’exécutable dans les répertoires déclarés dans cette variable d’environnement.

# 11. Vérifications après installation

Sur `ansible-master` :

```bash
whoami
which ansible
ansible --version
```

Le contexte attendu pour les TPs est :

```text
utilisateur : datascientest
machine     : ansible-master
Ansible     : accessible depuis le PATH
```

Pourquoi vérifier `whoami` ?

Parce que les fichiers Ansible placés dans le répertoire personnel d’un utilisateur sont lus dans le contexte de cet utilisateur.

Le corpus pratique insiste notamment sur le risque de travailler accidentellement sous un autre compte puis de chercher un `ansible.cfg`, une clé SSH ou un fichier d’inventaire dans le mauvais répertoire personnel.

---

# 12. Le fichier `ansible.cfg`

`ansible.cfg` permet de modifier le comportement d’Ansible.

Le support rappelle l’ordre de recherche suivant :

```text
1. ANSIBLE_CONFIG
        ↓
2. ./ansible.cfg
        ↓
3. ~/.ansible.cfg
        ↓
4. /etc/ansible/ansible.cfg
```

Autrement dit, Ansible recherche en priorité :

1. le fichier indiqué par la variable d’environnement `ANSIBLE_CONFIG` si elle est définie ;
2. `ansible.cfg` dans le répertoire courant ;
3. `~/.ansible.cfg` dans le répertoire personnel ;
4. `/etc/ansible/ansible.cfg`.

Le support signale également le risque de charger une configuration depuis un répertoire non sûr et accessible en écriture à d’autres utilisateurs.

---

## 12.1 Voir la configuration utilisée

```bash
ansible --version
```

La sortie indique notamment la configuration chargée.

Le support montre également comment générer un exemple de configuration :

```bash
ansible-config init --disabled > ansible.cfg
```

et une variante plus complète incluant les plugins :

```bash
ansible-config init --disabled -t all > ansible.cfg
```

---

## 12.2 Configuration minimale du lab

Le laboratoire Multipass utilise une configuration volontairement minimale :

```ini
[defaults]
host_key_checking = False
interpreter_python = auto_silent
```

### `host_key_checking = False`

Dans le lab local, cette option évite les interactions liées aux clés d’hôtes SSH lorsque les VMs pédagogiques sont recréées et changent d’identité ou d’adresse.

Elle doit être comprise ici comme une **commodité du laboratoire jetable**, pas comme une instruction générale à copier sans analyse dans tous les environnements.

### `interpreter_python = auto_silent`

Le corpus pratique utilise cette valeur pour demander à Ansible de détecter automatiquement l’interpréteur Python des cibles tout en évitant certains messages d’avertissement pendant le TP.

# 13. SSH : fondation du lab

Le guide Multipass remplace la clé `.pem` du scénario AWS par une clé générée directement depuis le master :

```bash
multipass shell ansible-master
su - datascientest
ssh-keygen -t rsa -b 4096
```

Cette clé est ensuite déployée sur les cibles dans le lab 01.

Le modèle visé devient :

```text
/home/datascientest/.ssh/
├── clé privée       → reste sur ansible-master
└── clé publique     → copiée vers cible1/2/3
```

```text
ansible-master
     │
     ├── SSH key ───► cible1
     ├── SSH key ───► cible2
     └── SSH key ───► cible3
```

La clé privée ne doit jamais être ajoutée au dépôt Git.

# 14. Particularité rencontrée avec Ubuntu 24.04

Le corpus enrichi documente une difficulté importante rencontrée dans le lab : sur l’environnement Ubuntu 24.04 utilisé, la configuration SSH issue de cloud-init peut conserver une directive `PasswordAuthentication no` dans :

```text
/etc/ssh/sshd_config.d/60-cloudimg-settings.conf
```

Conséquence observée pendant le bootstrap :

```text
Permission denied (publickey)
```

Le lab 01 documente la procédure de correction utilisée pour pouvoir initialement copier la clé SSH vers les cibles.

Cette difficulté est volontairement conservée dans la documentation : elle fait partie du retour d’expérience pratique et apprend à distinguer :

```text
symptôme
   ↓
Permission denied (publickey)
   ↓
hypothèse
   ↓
authentification SSH refusée
   ↓
inspection de la configuration
   ↓
correction
   ↓
retest
```

Voir :

```text
labs/01-multipass-bootstrap/README.md
```
