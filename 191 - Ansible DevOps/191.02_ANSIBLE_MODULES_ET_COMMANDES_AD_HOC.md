# 2. Le rôle des modules dans Ansible

Le support de cours présente les **modules** comme des unités de code spécialisées dans une tâche précise. Ils constituent la couche fonctionnelle utilisée par Ansible pour agir sur les machines gérées.

Exemples de responsabilités :

```text
installer un paquet       → apt / yum
contrôler un service      → service
créer un répertoire       → file
copier un fichier         → copy
générer un fichier        → template
modifier une ligne        → lineinfile
modifier un bloc          → blockinfile
planifier une tâche       → cron
attendre une condition    → wait_for
exécuter une commande     → command / shell
collecter les facts       → setup
```

Modèle mental :

```text
┌──────────────────────┐
│      Utilisateur     │
└──────────┬───────────┘
           │
           │ playbook ou commande ad hoc
           ▼
┌──────────────────────┐
│       Ansible        │
└──────────┬───────────┘
           │
           │ module + arguments
           ▼
┌──────────────────────┐
│     Managed Node     │
│  état à inspecter /  │
│      modifier        │
└──────────────────────┘
```

Un module reçoit des arguments et retourne des informations structurées, généralement présentées par Ansible sous forme JSON/YAML dans la sortie de commande.

# 3. Premier exemple : le module `apt`

Le support introduit le module `apt` avec une tâche simple :

```yaml
- name: Installation d'apache via le module apt
  apt:
    name: apache2
    state: present
```

Cette écriture exprime un **état souhaité** : Apache doit être présent.

Le même module peut être appelé directement depuis le terminal dans une commande ad hoc, que nous verrons plus loin.

---

# 4. Idempotence

L’idempotence est un principe central du cours.

Une opération idempotente peut être réexécutée sans provoquer de nouvelle modification lorsque l’état cible est déjà atteint.

Exemple conceptuel :

```text
État initial
apache2 absent
     │
     │ apt state=present
     ▼
apache2 installé
changed=true
     │
     │ même opération une seconde fois
     ▼
apache2 déjà présent
changed=false
```

Cela permet de raisonner en termes d’**état désiré** plutôt qu’en simple suite de commandes impératives.

## Interpréter `changed`

Une sortie Ansible peut notamment contenir :

```json
"changed": true
```

Cela signifie qu’Ansible a modifié l’hôte.

À l’inverse :

```json
"changed": false
```

signifie qu’aucune modification n’a été nécessaire.

# 6. Collections et `ansible.builtin`

Le support indique que, dans les versions modernes d’Ansible, les modules sont distribués via des **collections**.

Les modules de base couramment utilisés appartiennent à :

```text
ansible.builtin
```

Par exemple :

```yaml
- name: Copier un fichier
  ansible.builtin.copy:
    src: test.txt
    dest: /tmp/test.txt
```

## Convention du dépôt

Les exemples historiques du cours utilisent souvent les noms courts :

```yaml
apt:
copy:
service:
```

Dans les nouveaux exemples ajoutés au dépôt, nous privilégions lorsque cela améliore la lisibilité les **FQCN** (*Fully Qualified Collection Names*) :

```yaml
ansible.builtin.apt:
ansible.builtin.copy:
ansible.builtin.service:
```

Cette convention est une normalisation du dépôt ; elle ne remplace pas les exemples historiques du support.

# 7. Panorama des modules étudiés

## 7.1 `apt`

Le cours utilise `apt` pour Debian / Ubuntu.

Exemple source :

```yaml
- name: Mettre à jour le cache et installer Apache
  apt:
    name: apache2
    state: latest
    update_cache: yes
```

Dans le lab Multipass Ubuntu 24.04, `apt` est le gestionnaire utilisé pour installer notamment Nginx.

---

## 7.2 `yum`

Le support présente également `yum` pour les distributions de la famille RHEL/CentOS/Fedora :

```yaml
- name: Installer httpd
  yum:
    name: httpd
    state: latest
    update_cache: yes
```

Le laboratoire actuel étant basé sur Ubuntu, ce module est étudié conceptuellement mais n’est pas utilisé dans le TP Multipass.

---

## 7.3 `service`

Le module `service` contrôle les services sur les machines distantes.

Exemple du cours :

```yaml
- name: Redémarrer le service httpd
  service:
    name: httpd
    state: restarted
```

Cas d’usage :

```text
started
stopped
restarted
reloaded
```

---

## 7.4 `file`

Le module `file` gère notamment :

- fichiers ;
- répertoires ;
- liens symboliques ;
- permissions.

Exemple :

```yaml
- name: Créer /etc/datascientest
  file:
    path: /etc/datascientest
    state: directory
    mode: "0755"
```

---

## 7.5 `copy`

Le module `copy` transfère des fichiers depuis le nœud de contrôle vers les hôtes distants.

Exemple du cours :

```yaml
- name: Copier un fichier
  copy:
    src: /datascientest-source/test
    dest: /datascientest-destination/test
    owner: datascientest
    group: admin
    mode: "0755"
```

En mode ad hoc :

```bash
ansible all -i inventaire -m copy -a "src=test.txt dest=/home/datascientest"
```

---

## 7.6 `template`

Le module `template` combine un fichier modèle et Jinja2 afin de produire un fichier final sur l’hôte cible.

Exemple du support :

```yaml
- name: Appliquer le modèle Nginx
  ansible.builtin.template:
    src: datascientest-templates/nginx.conf.j2
    dest: /etc/nginx/sites-available/default
```

La templatisation sera approfondie avec les playbooks et les rôles.

---

## 7.7 `lineinfile`

Utilisé pour garantir la présence ou la valeur d’une ligne donnée.

```yaml
- name: Garantir la présence d'une ligne
  lineinfile:
    path: /tmp/datascientest
    line: "Cette ligne doit exister dans le fichier"
    state: present
```

---

## 7.8 `blockinfile`

Utilisé lorsqu’il faut gérer un bloc de plusieurs lignes.

```yaml
- name: Insérer un bloc de configuration
  ansible.builtin.blockinfile:
    path: /etc/network/interfaces
    block: |
      iface eth1 inet static
          address 192.168.99.10
          netmask 255.255.255.0
```

---

## 7.9 `cron`

Le module `cron` permet de gérer les entrées crontab.

```yaml
- name: Sauvegarde quotidienne à minuit
  ansible.builtin.cron:
    name: "Sauvegarde quotidienne de la base de données"
    minute: "0"
    hour: "0"
    job: "/usr/local/bin/datascientest_backup.sh > /var/log/datascientest_backup.sh.log 2>&1"
```

---

## 7.10 `wait_for`

Le module `wait_for` attend qu’une condition soit satisfaite :

- port disponible ;
- fichier présent ;
- processus terminé ;
- chaîne détectée dans un fichier.

Exemple :

```yaml
- name: Attendre une chaîne dans un fichier
  ansible.builtin.wait_for:
    path: /tmp/datascientest
    search_regex: "La chaîne existe, continue"
```

# 8. `command` vs `shell`

Le cours distingue clairement les deux modules.

## `command`

`command` exécute une commande sans passer par un shell complet.

Conséquences présentées dans le support :

- les variables shell comme `$HOME` ne sont pas interprétées de la même manière ;
- les opérateurs shell tels que redirections et pipes ne sont pas disponibles ;
- le comportement est plus prévisible.

## `shell`

`shell` permet d’utiliser les fonctionnalités d’un shell :

```text
$HOME
$HOSTNAME
>
>>
|
&
```

Exemple du support :

```yaml
- name: Exécuter un script et ajouter la sortie à un log
  ansible.builtin.shell: datascientest_script.sh >> script.log
```

## Bonne pratique du cours

Le support recommande de choisir un module spécialisé lorsque celui-ci existe, et de réserver `command` / `shell` aux situations où aucun module dédié n’offre le comportement recherché.

```text
module spécialisé disponible ?
          │
     ┌────┴────┐
    oui        non
     │          │
     ▼          ▼
utiliser     command / shell
le module    si nécessaire
```

# 9. Modules personnalisés

Le cours rappelle qu’il est possible de développer ses propres modules.

Principes donnés dans le support :

- vérifier qu’un module équivalent n’existe pas déjà ;
- garder le module simple et spécifique ;
- définir une interface prévisible ;
- documenter les paramètres ;
- documenter les valeurs de retour ;
- tester le module ;
- envisager une collection lorsque le périmètre devient plus large.

# 10. Les commandes ad hoc

Une commande **ad hoc** permet d’exécuter directement un module depuis le terminal sans écrire de playbook.

Le support les positionne principalement pour :

- les tests ;
- les opérations ponctuelles ;
- les vérifications rapides ;
- la prise en main des modules.

Syntaxe générale du cours :

```bash
ansible [modèle] -i [fichier d'inventaire] -m [module] -a "[options de module]"
```

Décomposition :

```text
ansible cible1 -i inventaire -m copy -a "src=test.txt dest=/tmp/test.txt"
│       │        │             │       │
│       │        │             │       └── arguments du module
│       │        │             └────────── module
│       │        └──────────────────────── inventaire
│       └───────────────────────────────── cible / pattern
└───────────────────────────────────────── CLI Ansible
```

# 12. Tester la connectivité avec `ping`

Commande :

```bash
ansible all -i inventaire -m ping
```

Sortie observée dans l’adaptation Multipass :

```text
cible1 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

Le module `ping` ne correspond pas à l’outil ICMP classique : dans ce contexte, il permet de vérifier qu’Ansible peut établir la communication et exécuter son module sur l’hôte.

## Warning sur l’interpréteur Python

L’adaptation Ubuntu 24.04 documente un avertissement relatif à la détection automatique de Python 3.12.

La configuration utilisée dans le lab est :

```ini
[defaults]
host_key_checking = False
interpreter_python = auto_silent
```

Le rôle de `auto_silent`, tel que décrit dans cette adaptation, est de conserver la détection automatique sans afficher cet avertissement.

# 13. Copier un fichier avec `copy`

Créer un fichier :

```bash
echo "Bienvenue sur Datascientest" > test.txt
```

Le copier vers les cibles :

```bash
ansible all -i inventaire -m copy -a "src=test.txt dest=/home/datascientest/test.txt"
```

Première exécution attendue :

```text
CHANGED
changed=true
```

Une nouvelle exécution permet d’observer l’idempotence si le fichier distant correspond déjà au fichier source :

```text
SUCCESS
changed=false
```

# 14. Collecter les facts avec `setup`

Le support utilise `setup` pour collecter les informations système.

Toutes les informations :

```bash
ansible cible1 -i inventaire -m setup
```

Filtrer une information :

```bash
ansible cible1 -i inventaire -m setup -a "filter=ansible_virtualization_type"
```

Exercice du support : récupérer les informations mémoire.

```bash
ansible cible1 -i inventaire -m setup -a "filter=ansible_*_mb"
```

Les facts seront réutilisés plus tard dans les playbooks.

# 15. Installer Nginx avec `apt`

Le cours propose ensuite d’ajouter une seconde cible et d’installer Nginx.

Dans le lab Multipass, les trois cibles sont déjà disponibles.

Mettre à jour le cache APT :

```bash
ansible cible2 -i inventaire -b -m apt -a "update_cache=yes cache_valid_time=86400"
```

Installer Nginx :

```bash
ansible cible2 -i inventaire -b -m apt -a "name=nginx state=latest"
```

L’option :

```text
-b
```

active l’élévation de privilèges (*become*) nécessaire pour une opération système telle que l’installation d’un paquet.

Le support original utilise également une variable de mot de passe sudo dans l’inventaire. Dans le lab de ce dépôt, le bootstrap Multipass fournit déjà à l’utilisateur pédagogique les privilèges sudo nécessaires ; aucun mot de passe sudo réel n’est stocké dans Git.

# 16. Désinstaller Nginx

Commande du support :

```bash
ansible cible2 -i inventaire -b -m apt -a "name=nginx state=absent"
```

Résultat attendu lors de la suppression :

```text
CHANGED
changed=true
```

# 17. Lecture des états Ansible

Pendant les commandes ad hoc, on rencontre principalement :

```text
SUCCESS / ok
    │
    └── commande exécutée avec succès

CHANGED
    │
    └── commande réussie et état de la cible modifié

FAILED
    │
    └── exécution impossible ou erreur du module

UNREACHABLE
    │
    └── Ansible ne peut pas joindre la cible
```

Pour un débutant, il faut systématiquement distinguer :

```text
problème de connexion
        ≠
problème du module
        ≠
module réussi avec modification
        ≠
module réussi sans modification
```

# 18. Difficultés documentées dans l’adaptation Multipass

## 18.1 Mauvais utilisateur sur `ansible-master`

Symptôme :

```text
Ansible ne lit pas le fichier ~/ansible.cfg attendu
```

Diagnostic :

```bash
whoami
```

Correction :

```bash

```

---

## 18.2 Clé SSH non déployée

Test direct :

```bash
ssh datascientest@<IP_CIBLE>
```

La connexion doit fonctionner avec la clé configurée lors du lab 01.

---

## 18.3 `Permission denied (publickey)`

L’adaptation Ubuntu 24.04 documente le cas où l’authentification SSH reste désactivée dans :

```text
/etc/ssh/sshd_config.d/60-cloudimg-settings.conf
```

Cette difficulté est traitée en détail dans :

```text
labs/01-multipass-bootstrap/
```

Il ne faut pas reconfigurer les cibles au hasard : vérifier d’abord le bootstrap précédent.

---

## 18.4 Mauvaise adresse IP

Les IP Multipass sont propres à l’environnement local.

Toujours récupérer les valeurs actuelles depuis l’hôte :

```bash
multipass list
```

Puis adapter l’inventaire.

---

## 18.5 `UNREACHABLE`

Ordre de diagnostic conseillé :

```text
1. multipass list
2. ping réseau / présence VM
3. ssh datascientest@IP
4. clé privée disponible
5. inventaire correct
6. ansible.cfg lu par le bon utilisateur
7. ansible cible -m ping -vvvv
```

Le niveau `-vvvv` permet d’obtenir davantage de détails pour le diagnostic SSH.

# 19. Bonnes pratiques issues du support

Le support insiste sur quatre principes :

1. privilégier les modules spécialisés plutôt que `shell` / `command` ;
2. garder les modules personnalisés simples et spécifiques ;
3. proposer des paramètres cohérents et prévisibles ;
4. documenter et tester les modules personnalisés.

## Convention supplémentaire du dépôt

Pour les nouveaux exemples du repository :

```text
- conserver les exemples historiques du cours lorsqu’ils sont étudiés ;
- distinguer explicitement les adaptations Multipass ;
- ne pas publier de credentials ;
- privilégier les FQCN dans les nouveaux exemples ;
- utiliser les commandes ad hoc pour l’exploration et les opérations ponctuelles ;
- passer aux playbooks lorsqu’une automatisation doit être reproductible et versionnée.
```

     │

     │
     └── non

          ▼
