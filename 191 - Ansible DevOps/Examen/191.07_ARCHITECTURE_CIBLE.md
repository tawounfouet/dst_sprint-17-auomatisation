# 191.07 — Architecture cible de l’évaluation

## 1. Architecture minimale conforme à l’énoncé

```text
                       ┌────────────────────┐
                       │   ANSIBLE CONTROL  │
                       │       NODE         │
                       └─────────┬──────────┘
                                 │ SSH
                    ┌────────────┴────────────┐
                    │                         │
                    ▼                         ▼
          ┌──────────────────┐      ┌──────────────────┐
          │   SERVEUR WEB    │      │   SERVEUR DB     │
          │                  │      │                  │
          │ role prestashop  │      │ role mysql       │
          │ HTTP :80         │      │ MySQL :3306      │
          └────────┬─────────┘      └────────▲─────────┘
                   │                         │
                   └────── connexion SQL ───┘
```

## 2. Inventaire logique

```text
exam_app
├── web
│   └── web1
└── database
    └── db1
```

Exemple conceptuel :

```yaml
all:
  children:
    web:
      hosts:
        web1:
    database:
      hosts:
        db1:
```

Les IP ne doivent pas être figées dans la documentation canonique.

## 3. Mapping rôle → machine

| Groupe | Hôte | Rôle |
|---|---|---|
| `web` | `web1` | `prestashop` ou alternative web retenue |
| `database` | `db1` | `mysql` |

## 4. Flux réseau exigé

```text
client
  │
  │ HTTP :80
  ▼
web1
  │
  │ MySQL :3306
  ▼
db1
```

L’énoncé impose le besoin de communication entre le serveur web et la base.

## 5. Ordre d’orchestration recommandé

L’énoncé ne fixe pas explicitement l’ordre des plays. Pour une implémentation cohérente, la référence proposée est :

```text
1. DB
   ├── installer MySQL
   ├── démarrer le service
   ├── créer base
   └── préparer l’accès applicatif

2. WEB
   ├── installer dépendances
   ├── installer solution e-commerce
   ├── injecter paramètres DB
   └── démarrer service HTTP

3. VALIDATION
   ├── DB active
   ├── Web active
   ├── Web → DB
   └── HTTP accessible
```

Cet ordre est une proposition d’implémentation, pas une exigence textuelle du support.

## 6. Variante de durcissement pour le projet réel

La source conseille l’usage d’un utilisateur `root` de base de données pour la connexion distante.

Pour le projet final réel, une variante plus restrictive pourra être mise en œuvre avec un utilisateur applicatif dédié :

```text
prestashop_app
    ↓
privilèges limités à la base applicative
    ↓
MySQL
```

Si cette variante est retenue, elle devra être documentée comme une décision d’implémentation différente du conseil pédagogique source.

## 7. Frontière avec Terraform

Cette évaluation porte sur Ansible. La création des VM elle-même n’est pas demandée dans l’énoncé.

Dans une architecture plus large du Sprint 17 :

```text
Terraform
   ↓
provisionner infrastructure
   ↓
Ansible
   ↓
configurer OS / services / application
```

Cette articulation est une extension du parcours global, pas un critère de l’examen Ansible décrit ici.
