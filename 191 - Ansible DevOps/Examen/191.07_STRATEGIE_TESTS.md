# 191.07 — Stratégie de tests

## 1. Objectif

L’énoncé exige de fournir les logs des résultats de tests dans un fichier `.txt`. La stratégie ci-dessous organise ces tests de manière reproductible.

## 2. Niveaux de tests

```text
T0  statique
 ↓
T1  connectivité Ansible
 ↓
T2  rôle database
 ↓
T3  rôle web
 ↓
T4  intégration web → DB
 ↓
T5  exposition HTTP
 ↓
T6  relance
 ↓
T7  packaging
```

## 3. T0 — Validation statique

```bash
ansible-inventory -i inventory/hosts.yml --graph
ansible-playbook -i inventory/hosts.yml playbooks/site.yml --syntax-check
```

Attendu : aucune erreur de parsing ni de syntaxe.

## 4. T1 — Connectivité Ansible

```bash
ansible all -i inventory/hosts.yml -m ping
```

Attendu : tous les hôtes nécessaires retournent `SUCCESS`.

## 5. T2 — Validation du rôle MySQL

Vérifier au minimum :

- présence du paquet/service ;
- état actif du service ;
- présence de la base applicative ;
- présence de l’identité de connexion requise.

Exemples de contrôles :

```bash
ansible database -i inventory/hosts.yml -b -m command -a "systemctl is-active mysql"
```

La commande exacte de validation SQL dépendra de l’implémentation retenue.

## 6. T3 — Validation du rôle web

Vérifier :

- présence des fichiers applicatifs ;
- état du serveur HTTP ;
- configuration applicative ;
- écoute sur le port prévu.

Exemple :

```bash
ansible web -i inventory/hosts.yml -b -m shell -a "ss -tlnp | grep ':80'"
```

## 7. T4 — Test d’intégration Web → MySQL

Ce test est central car l’énoncé exige que le serveur web puisse communiquer avec la base.

Le test doit être exécuté **depuis l’hôte web** vers l’hôte DB.

À valider :

```text
résolution/adresse DB
      ↓
TCP :3306
      ↓
authentification
      ↓
accès à la base applicative
```

La commande précise dépendra du client MySQL installé et du mécanisme de secret retenu.

## 8. T5 — Validation HTTP

Depuis le control node ou une machine cliente :

```bash
curl -I http://<WEB_HOST>
```

Puis une requête de contenu :

```bash
curl -L http://<WEB_HOST> | head
```

Attendu : réponse HTTP exploitable de la solution web.

## 9. T6 — Relance

Exécuter une seconde fois :

```bash
ansible-playbook -i inventory/hosts.yml playbooks/site.yml
```

Analyser le `PLAY RECAP` et documenter les tâches qui changent encore.

## 10. T7 — Validation du rendu

Avant le ZIP :

```bash
git status
find . -type f | sort
```

Vérifier :

- absence de clés privées ;
- absence de mot de passe réel ;
- présence des rôles ;
- présence du playbook ;
- présence du fichier de logs.

## 11. Capturer les logs

Une méthode simple consiste à utiliser `tee` :

```bash
mkdir -p logs
ansible-playbook -i inventory/hosts.yml playbooks/site.yml 2>&1 | tee logs/deployment.txt
```

Puis compléter avec les validations :

```bash
{
  echo '=== INVENTORY ==='
  ansible-inventory -i inventory/hosts.yml --graph
  echo '=== PING ==='
  ansible all -i inventory/hosts.yml -m ping
  echo '=== HTTP ==='
  curl -I http://<WEB_HOST>
} 2>&1 | tee -a logs/tests.txt
```

Ne jamais écrire un secret dans les logs.

## 12. Matrice de preuve

| Test | Critère source couvert | Preuve |
|---|---|---|
| inventaire | scripts fonctionnels / architecture | graphe |
| ping | exécution Ansible | SUCCESS |
| MySQL | rôle DB | service + SQL |
| HTTP | rôle web | curl |
| Web → DB | communication obligatoire | connexion depuis web |
| relance | robustesse | PLAY RECAP |
| logs | livrable explicite | `.txt` |
| ZIP | livrable explicite | archive finale |
