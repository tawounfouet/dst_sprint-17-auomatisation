# 2. Pourquoi Ansible Vault ?

Les playbooks et fichiers de variables peuvent contenir des informations sensibles :

```text
mots de passe
clés API
identifiants techniques
clés SSH
configuration sensible
```

Les conserver en clair dans un repository crée un risque de divulgation.

Ansible fournit pour cela **Ansible Vault**, accessible avec :

```bash
ansible-vault
```

Le support DataScientest insiste sur une distinction essentielle : Vault protège les **données au repos**. Une fois les valeurs déchiffrées pour être utilisées par Ansible, leur manipulation doit toujours rester maîtrisée.

```text
fichier YAML en clair
        │
        ▼
ansible-vault encrypt
        │
        ▼
fichier chiffré
        │
        ▼
repository Git
        │
        ▼
Ansible + mot de passe Vault
        │
        ▼
valeurs disponibles pendant l’exécution
```

---

# 3. Fichiers chiffrés et variables chiffrées

Le support distingue :

- les **variables chiffrées**, déchiffrées lorsqu’elles sont nécessaires ;
- les **fichiers chiffrés**, chargés et déchiffrés par Ansible pour pouvoir exploiter leur contenu.

Le TP du cours utilise principalement le chiffrement d’un fichier complet :

```text
group_vars/production.yaml
```

---

# 4. Créer un nouveau fichier chiffré

La commande :

```bash
ansible-vault create monfichier.yaml
```

crée directement un fichier protégé.

Ansible demande :

```text
New Vault password:
Confirm New Vault password:
```

puis ouvre un éditeur afin de saisir le contenu.

Après sauvegarde :

```bash
cat monfichier.yaml
```

le fichier commence par une entête similaire à :

```text
$ANSIBLE_VAULT;1.1;AES256
```

Le contenu qui suit n’est plus lisible en clair.

---

# 5. Chiffrer un fichier existant

Pour protéger un fichier déjà existant :

```bash
ansible-vault encrypt monfichier.yaml
```

C’est la commande utilisée dans l’exercice guidé DataScientest pour :

```text
group_vars/production.yaml
```

Le flux est :

```text
production.yaml en clair
        │
        ▼
ansible-vault encrypt
        │
        ▼
production.yaml chiffré
```

---

# 6. Afficher un fichier chiffré

Pour consulter le contenu :

```bash
ansible-vault view monfichier.yaml
```

Le mot de passe Vault est demandé et le contenu est affiché sans nécessiter un `decrypt` permanent du fichier.

---

# 7. Modifier un fichier chiffré

Pour modifier le contenu :

```bash
ansible-vault edit monfichier.yaml
```

Le support présente cette commande comme le moyen de déchiffrer temporairement le fichier dans l’éditeur, puis de le rechiffrer après sauvegarde.

---

# 8. Changer le mot de passe Vault

La commande :

```bash
ansible-vault rekey monfichier.yaml
```

permet de remplacer le mot de passe de chiffrement.

Interaction attendue :

```text
Vault password:
New Vault password:
Confirm New Vault password:
Rekey successful
```

---

# 9. Déchiffrer un fichier

Pour revenir à un fichier en clair :

```bash
ansible-vault decrypt monfichier.yaml
```

Sortie attendue :

```text
Vault password:
Decryption successful
```

Après cette opération, le fichier n’est plus chiffré par Vault.

---

# 10. Les commandes essentielles

| Commande | Rôle |
|---|---|
| `ansible-vault create fichier.yaml` | créer un nouveau fichier chiffré |
| `ansible-vault encrypt fichier.yaml` | chiffrer un fichier existant |
| `ansible-vault view fichier.yaml` | afficher le contenu déchiffré |
| `ansible-vault edit fichier.yaml` | modifier le contenu |
| `ansible-vault rekey fichier.yaml` | changer le mot de passe |
| `ansible-vault decrypt fichier.yaml` | remettre le fichier en clair |

---

# 11. Fournir le mot de passe lors d’un playbook

Le support présente deux méthodes.

## 11.1 `--ask-vault-pass`

Mode interactif :

```bash
ansible-playbook \
  -i inventaire.yaml \
  install_wordpress.yaml \
  --ask-vault-pass
```

Ansible demande :

```text
Vault password:
```

puis charge les valeurs protégées pendant l’exécution.

## 11.2 `--vault-password-file`

Le support Multipass présente une variante adaptée à l’automatisation :

```bash
echo "<VAULT_PASSWORD>" > ~/.vault_pass
chmod 600 ~/.vault_pass
```

Puis :

```bash
ansible-playbook \
  -i inventaire.yaml \
  install_wordpress.yaml \
  --vault-password-file ~/.vault_pass
```

Le fichier peut aussi être référencé dans `ansible.cfg` :

```ini
[defaults]
vault_password_file = ~/.vault_pass
```

Cette configuration reste optionnelle dans nos labs afin de ne pas imposer un fichier local particulier.

---

# 12. Ne jamais versionner le mot de passe Vault

Le support demande explicitement de ne pas publier le fichier de mot de passe.

Il recommande :

```bash
chmod 600 ~/.vault_pass
```

et :

```gitignore
.vault_pass
```

Notre repository reprend cette règle depuis son bootstrap.

```text
repository Git
├── playbooks
├── rôles
├── fichiers Vault chiffrés
└── .gitignore

hors repository
└── mot de passe Vault
```

# 13. Exercice guidé DataScientest

Le support propose de sécuriser :

```text
group_vars/production.yaml
```

avec :

```bash
ansible-vault encrypt group_vars/production.yaml
```

puis de relancer :

```bash
ansible-playbook -i inventaire.yaml install_wordpress.yaml --ask-vault-pass
```

Le mécanisme pédagogique est donc :

```text
group_vars/production.yaml
          │
          │ encrypt
          ▼
$ANSIBLE_VAULT;...
          │
          │ --ask-vault-pass
          ▼
install_wordpress.yaml
          │
          ▼
role wordpress
```

# 14. Adaptation au Lab 05 WordPress

Dans le support historique, le fichier `group_vars/production.yaml` contient notamment des variables de connexion et d’élévation de privilèges.

Dans notre parcours Multipass, la connexion SSH par clé a déjà été préparée dans les labs précédents. Le Lab 05 possède toutefois une variable applicative volontairement laissée sous forme de placeholder :

```yaml
wp_db_password: CHANGE_ME_WITH_VAULT
```

Le Lab 06 protège donc ce fichier en reprenant la même mécanique que le support DataScientest.

```text
production.example.yaml
          │
          │ copie locale
          ▼
production.yaml
          │
          │ remplacer le placeholder localement
          ▼
ansible-vault encrypt
          │
          ▼
production.yaml chiffré
```

Aucun mot de passe réel provenant des supports historiques n’est réintroduit dans le repository public.

---

# 15. Exemple adapté

Le fichier d’exemple du lab contient uniquement des valeurs publiables :

```yaml
---
ansible_user: datascientest
ansible_ssh_private_key_file: ~/.ssh/id_rsa
wp_db_password: CHANGE_ME_WITH_VAULT
```

L’apprenant crée localement :

```bash
cp group_vars/production.example.yaml group_vars/production.yaml
```

puis remplace le placeholder avant chiffrement.

Ensuite :

```bash
ansible-vault encrypt group_vars/production.yaml
```

Le fichier `production.yaml` peut alors être reconnu grâce à son en-tête :

```bash
head -n 1 group_vars/production.yaml
```

Résultat attendu :

```text
$ANSIBLE_VAULT;...
```

# 16. Vérifier un fichier Vault

Plusieurs commandes du support permettent de contrôler le résultat.

Afficher :

```bash
ansible-vault view group_vars/production.yaml
```

Modifier :

```bash
ansible-vault edit group_vars/production.yaml
```

Changer de mot de passe :

```bash
ansible-vault rekey group_vars/production.yaml
```

Déchiffrer explicitement si nécessaire :

```bash
ansible-vault decrypt group_vars/production.yaml
```

Pour le TP, le fichier doit normalement rester chiffré après validation.

# 18. Alternative avec fichier de mot de passe

Pour reproduire l’alternative du support :

```bash
printf '%s\n' '<VAULT_PASSWORD>' > ~/.vault_pass
chmod 600 ~/.vault_pass
```

Puis :

```bash
ansible-vault view \
  group_vars/production.yaml \
  --vault-password-file ~/.vault_pass
```

ou :

```bash
ansible-playbook \
  -i inventaire.yaml \
  install_wordpress.yaml \
  --vault-password-file ~/.vault_pass
```

# 19. Ce que Vault ne garantit pas

Le support indique explicitement que Vault protège les données **au repos**.

Il faut donc retenir :

```text
Vault
  = protection du secret stocké
  ≠ protection automatique de toutes ses utilisations
```

Ce chapitre ne prétend pas couvrir des mécanismes supplémentaires qui ne figurent pas dans les supports fournis ; il se concentre sur le périmètre enseigné : chiffrement, consultation, modification, rotation, déchiffrement et fourniture du mot de passe au playbook.
