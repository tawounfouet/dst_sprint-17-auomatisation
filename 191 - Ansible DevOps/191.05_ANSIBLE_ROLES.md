# 2. Pourquoi passer des playbooks aux rôles ?

Le chapitre précédent nous a permis de structurer un déploiement à l’aide de plusieurs playbooks. Cette approche fonctionne, mais elle devient plus difficile à maintenir lorsque le nombre de composants augmente.

Un projet basé uniquement sur des playbooks peut progressivement ressembler à ceci :

```text
install_wordpress.yaml
mysql.yaml
wordpress.yaml
nginx.yaml
modeles/
├── nginx-vhost.j2
└── wp-config.php.j2
```

Avec un rôle, le même domaine fonctionnel est regroupé dans une structure standardisée :

```text
roles/
└── wordpress/
    ├── defaults/
    ├── files/
    ├── handlers/
    ├── meta/
    ├── tasks/
    ├── templates/
    ├── tests/
    └── vars/
```

Le support DataScientest insiste sur trois bénéfices principaux :

```text
réutilisation
    +
partage
    +
organisation standardisée
```

Un rôle permet de regrouper un ensemble logique de tâches et de ressources sans dupliquer tout le contenu dans chaque playbook.

---

# 3. Playbook vs rôle

| Playbook | Rôle |
|---|---|
| décrit une orchestration | encapsule un composant réutilisable |
| contient souvent plusieurs tâches directement | répartit le contenu dans une structure standard |
| peut devenir volumineux | favorise la séparation des préoccupations |
| réutilisation plus limitée | appelable depuis plusieurs playbooks |
| templates/variables souvent gérés à côté | templates/variables intégrés au rôle |
| pas destiné en lui-même à Galaxy | rôle partageable via Ansible Galaxy |

Le rôle ne remplace pas le playbook d’orchestration. Il est **appelé par celui-ci**.

```text
playbook principal
      │
      └── roles:
            └── wordpress
                    │
                    ├── defaults
                    ├── tasks
                    ├── handlers
                    └── templates
```

---

# 4. Structure standard d’un rôle

La commande utilisée dans le cours est :

```bash
mkdir -p roles
cd roles
ansible-galaxy init wordpress
```

Ansible crée une arborescence de rôle.

```text
wordpress/
├── README.md
├── defaults/
│   └── main.yml
├── files/
├── handlers/
│   └── main.yml
├── meta/
│   └── main.yml
├── tasks/
│   └── main.yml
├── templates/
├── tests/
│   ├── inventory
│   └── test.yml
└── vars/
    └── main.yml
```

Le support mentionne également `library/` comme répertoire utile lorsque le rôle embarque des modules ou plugins personnalisés, même s’il n’est pas nécessairement généré par `ansible-galaxy init`.

# 5. Rôle de chaque répertoire

## 5.1 `defaults/`

Contient les variables par défaut du rôle.

```text
roles/wordpress/defaults/main.yml
```

Le TP y place notamment :

```yaml
wp_db_collate: ""
wp_table_prefix: "datascientest_"
wp_debug: false
wp_admin_email: "admin@example.invalid"

wp_version: latest
wp_install_dir: "/var/www/html"
wp_sitename: wordpress.local
wp_webserver: nginx
wp_db_name: "datascientest"
wp_db_user: "datascientest"
wp_db_host: "localhost"
wp_db_charset: "utf8"
```

Dans le dépôt public, le mot de passe MySQL du support n’est pas publié en clair. Il est remplacé par une variable à fournir depuis l’extérieur du rôle, puis chiffrée avec Vault dans le chapitre suivant.

---

## 5.2 `tasks/`

Contient les tâches du rôle.

Le point d’entrée conventionnel est :

```text
roles/wordpress/tasks/main.yml
```

Le TP ajoute aussi :

```text
roles/wordpress/tasks/nginx.yaml
```

puis l’inclut conditionnellement :

```yaml
- include_tasks: nginx.yaml
  when: wp_webserver == "nginx"
```

Le rôle peut ainsi séparer les tâches liées au serveur web des tâches WordPress/MySQL.

---

## 5.3 `handlers/`

Contient les handlers associés au rôle.

Exemple du support :

```yaml
---
- name: Nginx - Redémarrage
  service:
    name: nginx
    state: restarted
```

Un handler n’est exécuté que lorsqu’il est notifié par une tâche ayant signalé un changement.

```text
template modifié
      │
      └── notify
            │
            ▼
     handler Nginx
```

---

## 5.4 `templates/`

Contient les templates Jinja2 du rôle.

Dans le TP WordPress :

```text
templates/
├── nginx-vhost.j2
└── wp-config.php.j2
```

Les tâches du rôle peuvent les référencer directement par leur nom :

```yaml
- name: WordPress - Copie du fichier wp-config.php
  template:
    src: wp-config.php.j2
    dest: "{{ wp_install_dir }}/wordpress/wp-config.php"
```

---

## 5.5 `files/`

Contient les fichiers statiques destinés à être copiés sans rendu Jinja2.

Le TP ne nécessite pas de fichier statique spécifique, mais le répertoire fait partie de la structure standard.

---

## 5.6 `vars/`

Contient les variables du rôle ayant une priorité différente de celles placées dans `defaults/`.

Le support indique que les variables déclarées dans `vars/` ont une priorité relativement élevée. Il est donc préférable de réserver ce répertoire aux valeurs qui doivent réellement être imposées par le rôle.

---

## 5.7 `meta/`

Contient les métadonnées du rôle, notamment les informations utiles à son partage et, selon les usages, ses dépendances.

---

## 5.8 `tests/`

Le squelette généré peut contenir :

```text
tests/
├── inventory
└── test.yml
```

Le syllabus DataScientest mentionne également Molecule comme compétence de test à acquérir. Le cours Roles fourni ne développe toutefois pas Molecule : il n’est donc pas traité comme contenu source de ce chapitre. Il pourra être ajouté ultérieurement dans une extension dédiée.

# 6. Où Ansible recherche-t-il les rôles ?

Le support indique qu’Ansible recherche notamment les rôles :

1. relativement au playbook d’orchestration ;
2. dans un répertoire `roles/` ;
3. dans les chemins configurés via `roles_path` dans `ansible.cfg`.

Un rôle peut également être référencé explicitement par chemin.

Dans notre lab, le layout est simple :

```text
05-roles-wordpress/
├── install_wordpress.yaml
└── roles/
    └── wordpress/
```

Le rôle est donc découvert sans configuration supplémentaire de `roles_path`.

# 7. Transformation du projet WordPress en rôle

Le TP précédent utilisait plusieurs fichiers d’orchestration. Le chapitre Roles demande de transformer cette logique en rôle réutilisable.

Le projet cible devient :

```text
roles-wordpress-datascientest/

├── inventaire.yaml
├── install_wordpress.yaml
├── group_vars/
│   └── production.yaml
├── host_vars/
│   └── serveurweb1.yaml

        ├── handlers/main.yml

```

```text

    │
    └── cible1
          │
          └── serveurweb1
                │
                └── groupe production
```

Dans cet exercice, WordPress, Nginx/PHP et MySQL sont installés sur la même machine, conformément au support pédagogique.

# 8. Playbook principal

Une fois le rôle créé, le playbook principal devient très court :

```yaml
---
- name: Déployer WordPress avec le rôle dédié
  hosts: production
  become: true
  roles:
    - wordpress
```

C’est précisément l’intérêt du rôle : le playbook décrit **quoi orchestrer**, tandis que le rôle contient **comment configurer le composant**.


# 11. Téléchargement et installation de WordPress

Le support utilise `unarchive` avec `remote_src` afin de récupérer directement l’archive WordPress.

```yaml
- name: WordPress - Extraction de l'archive
  unarchive:
    src: "https://wordpress.org/wordpress-{{ wp_version }}.tar.gz"
    dest: "{{ wp_install_dir }}"
    remote_src: true
```

Il récupère ensuite les sels WordPress via l’API officielle :

```yaml
- name: WordPress - Récupération des sels
  delegate_to: localhost
  uri:
    url: https://api.wordpress.org/secret-key/1.1/salt/
    return_content: true
  become: false
  register: wp_salt_array
```

puis :

```yaml
- name: WordPress - Définition du fait wp_salt
  set_fact:
    wp_salt: "{{ wp_salt_array.content }}"
```

Le template `wp-config.php.j2` consomme ensuite ces valeurs.

# 12. Séparer Nginx avec `include_tasks`

Le support isole les tâches Nginx dans :

```text
tasks/nginx.yaml
```

et les charge uniquement si :

```yaml
when: wp_webserver == "nginx"
```

Cela permet de garder `tasks/main.yml` lisible tout en conservant un rôle unique pour l’exercice pédagogique.

```text
tasks/main.yml
      │
      ├── WordPress
      ├── MySQL
      │
      └── include_tasks
            │
            └── nginx.yaml
```

# 13. Détection de PHP-FPM

Le TP utilise une commande shell afin d’identifier la version du paquet PHP-FPM installée :

```yaml
- name: Nginx - Détermination de l'emplacement du socket PHP FPM
  shell: >-
    dpkg -l | grep php-fpm | awk '{print $3}' |
    grep -o '[0-9]\.[0-9]' | head -n 1
  register: php_ver
```

Puis le template Nginx utilise :

```nginx
fastcgi_pass unix:/var/run/php/php{{ php_ver.stdout }}-fpm.sock;
```

Cette approche est celle du support. Le lab la conserve pour rester fidèle au parcours pédagogique.

# 14. Incident Nginx rencontré dans le TP

Le support Multipass documente un cas important : le playbook peut terminer sans erreur alors que :

```bash
curl http://<IP_CIBLE1>
```

ne retourne pas le site attendu.

La cause observée est le vhost Nginx par défaut :

```text
/etc/nginx/sites-enabled/default
```

qui peut masquer la configuration WordPress placée dans :

```text
/etc/nginx/conf.d/wordpress.conf
```

Le diagnostic proposé dans le support consiste notamment à vérifier :

```bash
ss -tlnp | grep ':80'
nginx -t
ls /var/run/php/
cat /etc/nginx/conf.d/wordpress.conf
ls /etc/nginx/sites-enabled/
```

La correction pédagogique est d’ajouter au rôle :

```yaml
- name: Nginx - Suppression du vhost par défaut
  file:
    path: /etc/nginx/sites-enabled/default
    state: absent
  notify: Nginx - Redémarrage
```

Le lab 05 reprend explicitement cette correction.

# 15. Handler Nginx

Le support utilise un handler pour centraliser le redémarrage :

```yaml
---
- name: Nginx - Redémarrage
  service:
    name: nginx
    state: restarted
```

Les tâches qui modifient la configuration peuvent alors écrire :

```yaml
notify:
  - Nginx - Redémarrage
```

Cela évite de redémarrer Nginx systématiquement à chaque tâche.

# 21. Idempotence et relecture du rôle

Le rôle doit pouvoir être exécuté plusieurs fois sans obliger l’apprenant à reconstruire la VM à chaque test.

Il faut notamment observer :

```text
première exécution
changed > 0

seconde exécution
beaucoup plus de ok
moins de changed
```

Certaines opérations du support, comme la récupération dynamique des sels ou certaines commandes shell, peuvent continuer à signaler des changements. Le lab sert justement à observer ces comportements avant d’aborder les bonnes pratiques transverses plus tard dans le module.

# 22. Ansible Galaxy

Le support présente **Ansible Galaxy** comme un référentiel permettant de publier et récupérer des rôles et collections.

La commande `ansible-galaxy` permet notamment de :

```text
créer un rôle
installer un rôle
installer depuis Galaxy ou Git
supprimer certains contenus installés
interagir avec les ressources Galaxy
```

Dans ce chapitre, son usage principal est :

```bash
ansible-galaxy init wordpress
```

Le rôle créé localement n’est pas publié sur Galaxy dans le cadre du TP fourni.

# 23. Ce que le rôle change dans notre architecture pédagogique

Avant :

```text
Playbooks
├── wordpress.yaml
├── nginx.yaml
├── mysql.yaml
└── install_wordpress.yaml
```

Après :

```text
Playbook d'orchestration
└── install_wordpress.yaml
        │
        ▼
Role wordpress
├── defaults
├── tasks
├── handlers
├── templates
└── meta/tests/vars/files
```

Le niveau d’abstraction augmente :

```text
commande ad hoc
      ↓
playbook
      ↓
rôle
      ↓
réutilisation / partage
```
