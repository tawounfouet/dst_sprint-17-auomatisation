# 2. Pourquoi passer des playbooks aux rôles ?

Le chapitre précédent nous a permis d’écrire des playbooks contenant plusieurs tâches, variables, handlers et templates.

Cette approche fonctionne très bien tant que le projet reste petit :

```text
playbook.yaml
├── installation
├── configuration
├── template
├── handler
└── validation
```

Lorsque le nombre de composants augmente, le fichier devient cependant plus difficile à maintenir.

```text
playbook-monolithique.yaml
├── PHP
├── Nginx
├── WordPress
├── MySQL
├── utilisateurs
├── fichiers
├── templates
├── handlers
├── variables
└── conditions
```

Le support DataScientest introduit les rôles comme une manière de **réutiliser et partager efficacement le code Ansible**, tout en lui donnant une structure normalisée.

Le rôle permet de passer à une organisation de ce type :

```text
playbook d'orchestration
        │
        ▼
roles:
  - wordpress
        │
        ▼
roles/wordpress/
├── tasks/
├── handlers/
├── templates/
├── files/
├── defaults/
├── vars/
├── meta/
└── tests/
```

Le playbook indique **quoi orchestrer** ; le rôle contient **comment le composant est configuré**.

---

# 3. Playbook et rôle : responsabilités différentes

| Playbook | Rôle |
|---|---|
| décrit une orchestration | encapsule une responsabilité réutilisable |
| cible des groupes d’hôtes | contient tâches, variables et fichiers associés |
| peut appeler plusieurs rôles | peut être réutilisé dans plusieurs playbooks |
| très lisible lorsqu’il reste court | maintient la complexité dans une structure standard |

Exemple :

```yaml
- name: Déployer WordPress
  hosts: production
  become: true
  roles:
    - wordpress
```

Le playbook principal devient volontairement minimal.

# 4. Création d’un rôle avec Ansible Galaxy

Le cours utilise :

```bash
mkdir -p roles
cd roles
ansible-galaxy init wordpress
```

Sortie attendue :

```text
- Role wordpress was created successfully
```

La commande génère une structure standard de rôle.

Pour inspecter la commande :

```bash
ansible-galaxy role --help
```

ou, selon la version d’Ansible :

```bash
ansible-galaxy --help
```

# 5. Structure d’un rôle Ansible

Une structure classique est :

```text
roles/
└── wordpress/
    ├── README.md
    ├── defaults/
    │   └── main.yml
    ├── files/
    ├── handlers/
    │   └── main.yml
    ├── meta/
    │   └── main.yml
    ├── tasks/
    │   └── main.yml
    ├── templates/
    ├── tests/
    │   ├── inventory
    │   └── test.yml
    └── vars/
        └── main.yml
```

## 5.1 `tasks/`

Contient les tâches exécutées par le rôle.

Le point d’entrée principal est :

```text
tasks/main.yml
```

Il peut inclure d’autres fichiers :

```yaml
- name: Charger la configuration Nginx
  ansible.builtin.include_tasks: nginx.yml
  when: wp_webserver == "nginx"
```

Cela évite de transformer `tasks/main.yml` en fichier monolithique.

---

## 5.2 `handlers/`

Contient les handlers déclenchés par `notify`.

```yaml
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

Une tâche peut notifier ce handler :

```yaml
- name: Installer le vhost WordPress
  ansible.builtin.template:
    src: nginx-vhost.j2
    dest: /etc/nginx/conf.d/wordpress.conf
  notify: Restart nginx
```

Le handler n’est exécuté que si la tâche qui le notifie a effectivement changé l’état de la machine.

---

## 5.3 `templates/`

Contient les modèles Jinja2 utilisés par le rôle.

Dans le TP WordPress :

```text
templates/
├── nginx-vhost.j2
└── wp-config.php.j2
```

Les variables du rôle peuvent y être injectées avec :

```jinja2
{{ wp_db_name }}
{{ wp_db_user }}
{{ wp_sitename }}
```

---

## 5.4 `files/`

Contient les fichiers statiques utilisés avec des modules tels que `copy`.

Exemple :

```yaml
- name: Copier un fichier statique
  ansible.builtin.copy:
    src: maintenance.html
    dest: /var/www/html/maintenance.html
```

Le chemin `src` peut être résolu automatiquement relativement au répertoire `files/` du rôle.

---

## 5.5 `defaults/`

Le support place dans `defaults/main.yml` les variables par défaut du rôle.

Exemple :

```yaml
wp_install_dir: /var/www/html/wordpress
wp_webserver: nginx
wp_db_name: wordpress
wp_db_user: wordpress
```

Ces valeurs servent de **defaults** : elles sont destinées à pouvoir être remplacées facilement depuis l’inventaire, `group_vars`, `host_vars` ou les paramètres du playbook.

C’est l’endroit privilégié pour les valeurs configurables qui définissent le comportement standard du rôle.

---

## 5.6 `vars/`

Le support rappelle que les variables placées dans `vars/main.yml` ont une priorité plus élevée que les defaults du rôle.

Elles conviennent davantage aux éléments internes du rôle que l’utilisateur ne doit normalement pas modifier.

Une règle de conception utile est donc :

```text
defaults/main.yml
    ↓
variables configurables par l'utilisateur

vars/main.yml
    ↓
variables internes du rôle
```

Éviter de placer toutes les options dans `vars/`, car cela rend le rôle beaucoup moins facilement surchargeable.

---

## 5.7 `meta/`

Contient les métadonnées du rôle : informations descriptives et éventuelles dépendances envers d’autres rôles.

Le fichier principal est :

```text
meta/main.yml
```

---

## 5.8 `tests/`

Le rôle généré par `ansible-galaxy init` peut contenir une petite structure de test :

```text
tests/
├── inventory
└── test.yml
```

Elle permet d’exécuter le rôle dans un contexte de validation simple.

Le syllabus DataScientest mentionne également **Molecule** dans les compétences du module ; sa mise en œuvre complète sera traitée plus tard dans les références/tests avancés, car le support de cours fourni pour ce chapitre ne détaille pas Molecule.

---

## 5.9 `library/`

Le support mentionne aussi un répertoire optionnel `library/`, non créé automatiquement par `ansible-galaxy init`, qui peut accueillir des modules ou plugins personnalisés utilisés par le rôle.

---

# 6. Où Ansible recherche-t-il les rôles ?

Le cours indique qu’un rôle peut être recherché notamment :

- relativement au playbook d’orchestration ;
- dans un répertoire `roles/` ;
- dans les chemins configurés par `roles_path`.

Exemple `ansible.cfg` :

```ini
[defaults]
roles_path = ./roles
```

Dans notre lab, le rôle se trouve directement dans :

```text
roles/wordpress/
```

et aucun chemin absolu spécifique à une machine n’est nécessaire.

# 10. Tâches principales

Le rôle doit réaliser les grandes étapes suivantes :

```text
WordPress role
│
├── installer PHP
├── installer Nginx
├── installer MySQL
├── télécharger WordPress
├── créer la base
├── créer l'utilisateur applicatif
├── générer wp-config.php
├── configurer Nginx
├── démarrer les services
└── appliquer les permissions
```

Dans le support, ces opérations sont regroupées dans `tasks/main.yml`, avec une inclusion séparée de `tasks/nginx.yaml`.

Le dépôt canonique conserve cette organisation mais utilise les noms qualifiés complets des modules (`ansible.builtin.*`) et la collection `community.mysql` pour les modules MySQL.

# 11. Collection MySQL

Les modules MySQL utilisés dans les anciens exemples de cours ne font pas partie de `ansible.builtin` dans les distributions modernes d’Ansible.

Le lab rend donc explicitement la dépendance visible :

```yaml
collections:
  - name: community.mysql
```

Installation :

```bash
ansible-galaxy collection install -r requirements.yml
```

Cette adaptation ne change pas l’objectif pédagogique du support : elle rend simplement la dépendance exécutable et explicite dans le projet.

# 12. Base de données et principe de moindre privilège

Le support original montre un utilisateur MySQL avec des privilèges très larges.

Dans le lab canonique, nous limitons l’utilisateur WordPress à sa base :

```yaml
priv: "{{ wp_db_name }}.*:ALL"
```

Le résultat attendu est :

```text
wordpress user
      │
      └── droits sur wordpress.*
```

et non :

```text
wordpress user
      └── droits sur toutes les bases
```

Cette différence est une mesure de durcissement du lab public ; elle n’est pas présentée comme faisant partie du texte original du cours.

# 13. Nginx et PHP-FPM

Le support adapte WordPress à Nginx et utilise un template de virtual host.

La configuration finale doit ressembler conceptuellement à :

```text
HTTP :80
   │
   ▼
Nginx
   │
   ├── fichiers statiques
   │
   └── *.php
         │
         ▼
     PHP-FPM
         │
         ▼
     WordPress
         │
         ▼
       MySQL
```

Le rôle détermine la version PHP installée puis s’assure que le service PHP-FPM correspondant est démarré.

# 15. Handlers

Le rôle utilise un handler pour Nginx.

```text
template modifié
      │
      └── notify
            │
            ▼
      Restart nginx
```

C’est préférable à un redémarrage inconditionnel à chaque exécution.

Un rôle bien conçu vise autant que possible :

```text
première exécution
changed > 0

seconde exécution
changed ≈ 0
```

---

# 16. `include_tasks`

Le support utilise une inclusion conditionnelle pour Nginx :

```yaml
- name: Charger les tâches Nginx
  ansible.builtin.include_tasks: nginx.yml
  when: wp_webserver == "nginx"
```

Cela permet de séparer :

```text
tasks/main.yml
    │
    ├── logique WordPress/MySQL
    │
    └── include_tasks
           │
           ▼
       tasks/nginx.yml
```

Cette technique devient utile lorsque le rôle supporte plusieurs variantes ou plusieurs composants.

---

# 17. Playbook d’orchestration

Le cours termine par un playbook très court :

```yaml
- hosts: production
  become: true
  roles:
    - wordpress
```

Le dépôt canonique conserve cette idée avec des noms de play explicites :

```yaml
- name: Déployer WordPress avec le rôle wordpress
  hosts: production
  become: true
  roles:
    - role: wordpress
```

Le point important est la séparation :

```text
install_wordpress.yaml
      │
      └── orchestration

roles/wordpress/
      │
      └── implémentation
```

# 21. Ansible Galaxy

Le support présente **Ansible Galaxy** comme un référentiel permettant de publier et de récupérer des rôles et collections.

La commande `ansible-galaxy` sert notamment à :

```text
créer un rôle
installer un rôle
installer une collection
inspecter les commandes Galaxy
réutiliser du contenu communautaire
```

Exemples :

```bash
ansible-galaxy init roles/mon_role
```

```bash
ansible-galaxy role install nom_du_role
```

```bash
ansible-galaxy collection install community.mysql
```

Dans les projets plus importants, les dépendances doivent être déclarées explicitement afin qu’un autre utilisateur puisse reconstruire l’environnement.

# 22. Anti-patterns importants

## 22.1 Tout mettre dans `tasks/main.yml`

```text
❌ 500 lignes dans tasks/main.yml
```

Préférer :

```text
✅ tasks/main.yml
   ├── include web
   ├── include database
   └── include validation
```

lorsque la taille du rôle le justifie.

---

## 22.2 Mettre tous les réglages dans `vars/main.yml`

Cela rend les variables difficiles à surcharger.

Préférer `defaults/main.yml` pour les paramètres configurables.

---

## 22.3 Redémarrer les services à chaque exécution

Préférer les handlers et `notify`.

---

## 22.4 Utiliser `shell` pour tout

Le support utilise `shell` pour déterminer le socket/version PHP. Dans le lab canonique, une commande sans pipeline est préférée lorsque cela suffit, avec `changed_when: false` pour éviter de déclarer un changement artificiel.

Le lab n’embarque aucun secret réel.

# 23. Troubleshooting

## `role 'wordpress' was not found`

Vérifier :

```bash
find roles -maxdepth 2 -type f | sort
```

et :

```bash
ansible-config dump | grep -i roles_path
```

Le rôle doit être dans un chemin connu d’Ansible.

---

## `couldn't resolve module/action 'community.mysql.mysql_db'`

Installer la collection :

```bash
ansible-galaxy collection install -r requirements.yml
```

Puis vérifier :

```bash
ansible-galaxy collection list | grep community.mysql
```

---

## `UNREACHABLE`

Revenir aux contrôles des labs précédents :

```bash
ansible production -i inventaire.example.yaml -m ansible.builtin.ping -vvvv
```

Vérifier l’IP, l’utilisateur et la clé SSH.

---

## Nginx actif mais page incorrecte

Vérifier :

```bash
sudo nginx -t
sudo cat /etc/nginx/conf.d/wordpress.conf
sudo ls -la /var/www/html/wordpress
```

Le support Multipass insiste sur la suppression du site Nginx par défaut lorsque celui-ci masque le vhost WordPress.

---

## PHP-FPM non démarré

Vérifier les services disponibles :

```bash
systemctl list-unit-files 'php*-fpm.service'
```

Puis :

```bash
php -r 'echo PHP_MAJOR_VERSION.".".PHP_MINOR_VERSION;'
```

# 24. Validation automatique

Le lab fournit :

```bash
./scripts/verify_role.sh
```

Le script vérifie au minimum :

```text
ansible-playbook disponible

collection community.mysql
inventaire parsable
syntaxe du playbook
```

Les vérifications de services ne sont effectuées qu’après un déploiement réel.

# 25. Ce qu’il faut retenir

```text
PLAYBOOK
    │
    │ orchestre
    ▼
ROLE
├── defaults
├── tasks
├── handlers
├── templates
├── files
├── vars
├── meta
```

Un rôle n’est pas simplement un dossier supplémentaire : c’est une **unité de conception et de réutilisation** qui permet de faire évoluer un projet Ansible sans faire grossir indéfiniment ses playbooks.
