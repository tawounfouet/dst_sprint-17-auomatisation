# 2. Du mode ad hoc au playbook

Les chapitres précédents nous ont permis de lancer des actions unitaires :

```bash
ansible all -i inventaire.yaml -m ping
ansible cible1 -i inventaire.yaml -m setup
ansible cible2 -i inventaire.yaml -b -m apt -a "name=nginx state=present"
```

Ces commandes sont utiles pour tester, inspecter ou effectuer une action ponctuelle.

Dès que plusieurs opérations doivent être exécutées dans un ordre reproductible, le support DataScientest introduit les **playbooks**.

```text
Commande ad hoc
      │
      │ action ponctuelle
      ▼
┌───────────────┐
│   1 module    │
└───────────────┘

Playbook
      │
      │ orchestration reproductible
      ▼
┌───────────────┐
│ Play 1        │
│ ├── Task 1    │
│ ├── Task 2    │
│ └── Task 3    │
├───────────────┤
│ Play 2        │
│ ├── Task 1    │
│ └── Task 2    │
└───────────────┘
```

Le support définit le playbook comme un fichier YAML contenant un ou plusieurs **plays**, utilisés pour décrire l’état souhaité de systèmes distants et orchestrer des tâches ordonnées.

# 3. Vocabulaire essentiel

## 3.1 Playbook

Le fichier YAML complet.

```text
datascientest-playbook.yaml
```

## 3.2 Play

Un play associe un ensemble d’hôtes à une liste de tâches.

```yaml
- name: Configuration des serveurs web
  hosts: serveurweb
  become: true
  tasks:
    ...
```

## 3.3 Task

Une tâche représente une action nommée.

```yaml
- name: Installer Apache2
  ansible.builtin.apt:
    name: apache2
    state: present
```

## 3.4 Module

La tâche appelle un module Ansible :

```text
apt
service
copy
template
file
user
shell
...
```

Le support source utilise principalement les noms courts (`apt`, `service`, etc.). Dans les exemples canoniques de ce dépôt, nous privilégions les noms qualifiés comme `ansible.builtin.apt` afin de rendre explicite l’origine du module.

---

# 4. Structure minimale d’un playbook

```yaml
---
- name: Exemple de play
  hosts: serveurweb
  become: true

  tasks:
    - name: Installer Apache2
      ansible.builtin.apt:
        name: apache2
        state: present
```

Modèle mental :

```text
PLAYBOOK
└── PLAY
    ├── name
    ├── hosts
    ├── become
    └── tasks
        ├── TASK
        │   └── MODULE
        └── TASK
            └── MODULE
```

# 5. Le cas pratique principal : Apache + PostgreSQL

Le support construit un playbook à deux plays :

```text
serveurweb
    │
    ├── installer Apache2
    ├── démarrer Apache2
    └── déployer une page HTML

serveurdatabase
    │
    ├── installer PostgreSQL
    └── démarrer PostgreSQL
```

Dans notre adaptation Multipass :

```text
ansible-master
│
├── cible1 → serveurweb1      → groupe serveurweb
└── cible2 → serveurdatabase1 → groupe serveurdatabase
```

Les adresses IP réelles sont volontairement absentes du dépôt : elles doivent être récupérées avec `multipass list` puis placées dans les fichiers `host_vars` locaux.

# 6. Playbook principal

Version canonique du dépôt :

```yaml
---
- name: Configurer le serveur web Apache
  hosts: serveurweb
  become: true

  tasks:
    - name: Installer Apache2
      ansible.builtin.apt:
        name: apache2
        state: present
        update_cache: true
      tags:
        - web

    - name: Démarrer et activer Apache2
      ansible.builtin.service:
        name: apache2
        state: started
        enabled: true
      tags:
        - web

    - name: Déployer la page d’accueil
      ansible.builtin.template:
        src: ../templates/index.html.j2
        dest: /var/www/html/index.html
        mode: "0644"
      tags:
        - web

- name: Configurer le serveur PostgreSQL
  hosts: serveurdatabase
  become: true

  tasks:
    - name: Installer PostgreSQL
      ansible.builtin.apt:
        name: postgresql
        state: present
        update_cache: true
      tags:
        - db

    - name: Démarrer et activer PostgreSQL
      ansible.builtin.service:
        name: postgresql
        state: started
        enabled: true
      tags:
        - db
```

Le support original utilise `state: latest` pour PostgreSQL. Le lab canonique utilise `present` afin que le TP reste focalisé sur l’installation et l’idempotence, sans imposer une montée de version à chaque exécution. Cette différence est une convention du dépôt, pas une modification du contenu historique archivé.

# 7. Exécuter un playbook

Syntaxe de base :

```bash
ansible-playbook -i inventaire.yaml playbooks/datascientest-playbook.yaml
```

Avant d’exécuter :

```bash
ansible all -i inventaire.yaml -m ping
```

Puis :

```bash
ansible-playbook \
  -i inventaire.yaml \
  playbooks/datascientest-playbook.yaml
```

# 8. Lire le `PLAY RECAP`

Le support insiste sur le résumé final :

```text
PLAY RECAP
serveurweb1      : ok=4 changed=2 unreachable=0 failed=0 skipped=0 ...
serveurdatabase1 : ok=3 changed=1 unreachable=0 failed=0 skipped=0 ...
```

| Compteur | Interprétation dans le TP |
|---|---|
| `ok` | tâche exécutée sans changement nécessaire |
| `changed` | tâche ayant modifié l’état de la machine |
| `unreachable` | connexion à l’hôte impossible |
| `failed` | tâche en erreur |
| `skipped` | tâche ignorée, par exemple à cause d’une condition |
| `rescued` | tâche récupérée par un bloc de secours |
| `ignored` | erreur explicitement ignorée |

Un objectif important du lab est d’obtenir :

```text
unreachable=0
failed=0
```

# 9. Idempotence et seconde exécution

Après une première exécution réussie, relancer :

```bash
ansible-playbook -i inventaire.yaml playbooks/datascientest-playbook.yaml
```

L’état attendu est que les tâches déjà satisfaites soient majoritairement `ok` plutôt que `changed`.

```text
1re exécution
installations / fichiers
        ↓
changed

2e exécution
état déjà conforme
        ↓
ok
```

Cette observation relie directement les playbooks au principe d’idempotence introduit au chapitre 191.02.

# 10. Limiter l’exécution avec `--limit`

Le support présente `--limit` pour exécuter le playbook sur une cible précise.

```bash
ansible-playbook \
  -i inventaire.yaml \
  playbooks/datascientest-playbook.yaml \
  --limit serveurdatabase1
```

Autres exemples :

```bash
--limit serveurweb
--limit serveurdatabase
--limit serveurweb1
```

C’est particulièrement utile pour isoler un diagnostic ou tester une modification sur une seule cible.

# 11. Variables

Le support présente plusieurs emplacements possibles pour les variables.

```text
variables
├── vars: dans un play
├── group_vars/
├── host_vars/
├── vars_files:
├── register
└── -e / --extra-vars
```

## 11.1 Variables dans un play

```yaml
- name: Exemple
  hosts: serveurweb
  vars:
    serveurweb_message: "Datascientest ANSIBLE"
```

Utilisation :

```yaml
msg: "{{ serveurweb_message }}"
```

## 11.2 `group_vars`

```text
group_vars/
├── all.yaml
├── serveurweb.yaml
└── serveurdatabase.yaml
```

Exemple :

```yaml
# group_vars/serveurweb.yaml
tier: web
serveurweb_message: "Datascientest ANSIBLE"
```

## 11.3 `host_vars`

```text
host_vars/
├── serveurweb1.yaml
└── serveurdatabase1.yaml
```

Exemple :

```yaml
ansible_host: <IP_CIBLE1>
```

## 11.4 `vars_files`

Le support montre également :

```yaml
vars_files:
  - variables/datascientest_variables.yaml
```

## 11.5 Variables à l’exécution

```bash
ansible-playbook \
  -i inventaire.yaml \
  -e serveurweb_message="Message temporaire" \
  playbooks/datascientest-playbook.yaml
```

Le cours présente `-e` comme mécanisme de substitution de variables à l’exécution.

# 13. `register` et `debug`

Le support présente `register` comme moyen de capturer le résultat d’une tâche.

```yaml
- name: Vérifier la version Python
  ansible.builtin.command: python3 --version
  register: python_version
  changed_when: false

- name: Afficher le résultat
  ansible.builtin.debug:
    var: python_version
```

Le résultat enregistré est un dictionnaire pouvant contenir notamment :

```text
stdout
stderr
rc
changed
failed
```

Exemple plus ciblé :

```yaml
- name: Afficher stdout
  ansible.builtin.debug:
    msg: "{{ python_version.stdout }}"
```

Le support source montre `register` avec une tâche `shell` puis `debug`; le lab canonique utilise une commande non destructive pour faciliter la répétition.

# 14. Facts Ansible

Avant les tâches d’un play, Ansible collecte par défaut des informations sur les machines distantes.

Le support cite notamment :

- interfaces réseau ;
- adresses IP ;
- système d’exploitation ;
- mémoire ;
- CPU ;
- informations matérielles.

Flux :

```text
Début du play
    │
    ▼
Gathering Facts
    │
    ▼
ansible_facts
    │
    ▼
tasks
```

Exemple :

```yaml
- name: Afficher la famille OS
  ansible.builtin.debug:
    msg: "Famille OS : {{ ansible_facts['os_family'] }}"
```

Pour désactiver la collecte :

```yaml
gather_facts: false
```

Le support précise alors que les facts non collectés ne peuvent pas être utilisés par les tâches du play.

# 15. Conditions avec `when`

Le support utilise `when` pour contrôler le flux d’exécution.

```yaml
- name: Tâche réservée aux systèmes Debian
  ansible.builtin.debug:
    msg: "Système de famille Debian"
  when: ansible_facts['os_family'] == 'Debian'
```

Modèle mental :

```text
condition vraie  → task exécutée
condition fausse → task skipped
```

Les conditions peuvent s’appuyer sur :

```text
variables
facts
résultats enregistrés avec register
opérateurs logiques
```

# 16. Boucles avec `loop`

## 16.1 Liste simple

```yaml
- name: Créer plusieurs répertoires
  ansible.builtin.file:
    path: "/tmp/{{ item }}"
    state: directory
  loop:
    - datascientest-a
    - datascientest-b
    - datascientest-c
```

## 16.2 Dictionnaires

Le support montre une boucle de dictionnaires pour créer des fichiers avec des modes différents.

```yaml
- name: Créer des fichiers de démonstration
  ansible.builtin.file:
    state: touch
    path: "/tmp/{{ item.nom }}"
    mode: "{{ item.mode }}"
  loop:
    - { nom: "fichier1", mode: "0755" }
    - { nom: "fichier2", mode: "0775" }
    - { nom: "fichier3", mode: "0777" }
```

## 16.3 Boucle + condition

```yaml
- name: Afficher uniquement les valeurs supérieures à 90
  ansible.builtin.debug:
    msg: "{{ item }}"
  loop: [100, 200, 3, 600, 7, 11]
  when: item > 90
```

# 17. Réessayer avec `until`

Le support présente :

```yaml
register: logoutput
until: logoutput.stdout.find("success") != -1
retries: 10
delay: 15
```

Ce pattern permet de répéter une tâche jusqu’à satisfaction d’une condition.

Modèle :

```text
Task
 │
 ▼
condition ? ── oui ──► continuer
 │
 non
 │
 ▼
attendre delay
 │
 ▼
réessayer
```

Le lab ne dépend pas d’un journal externe pour ne pas introduire une fausse dépendance, mais le concept est documenté dans le chapitre.

# 18. Tags

Le support utilise les tags `web` et `db`.

```yaml
tags:
  - web
```

Exécuter seulement le web :

```bash
ansible-playbook \
  -i inventaire.yaml \
  --tags web \
  playbooks/datascientest-playbook.yaml
```

Exécuter seulement la base :

```bash
ansible-playbook \
  -i inventaire.yaml \
  --tags db \
  playbooks/datascientest-playbook.yaml
```

Ignorer le web :

```bash
ansible-playbook \
  -i inventaire.yaml \
  --skip-tags web \
  playbooks/datascientest-playbook.yaml
```

Lister les tags :

```bash
ansible-playbook \
  -i inventaire.yaml \
  --list-tags \
  playbooks/datascientest-playbook.yaml
```

Le support présente aussi les tags spéciaux :

```text
always
never
```

# 19. Jinja2 et le module `template`

Le support introduit Jinja2 comme langage de templates utilisé par Ansible pour générer dynamiquement des fichiers.

Délimiteurs présentés :

| Syntaxe | Usage |
|---|---|
| `{{ ... }}` | afficher une variable |
| `{% ... %}` | instruction de contrôle |
| `{# ... #}` | commentaire |

Template du lab :

```jinja
<!doctype html>
<html lang="fr">
<head>
  <meta charset="utf-8">
  <title>Ansible Datascientest</title>
</head>
<body>
  <h1>{{ serveurweb_message }}</h1>
  <p>Hôte Ansible : {{ inventory_hostname }}</p>
  <p>Tier : {{ tier }}</p>
</body>
</html>
```

Tâche :

```yaml
- name: Déployer la page d’accueil
  ansible.builtin.template:
    src: ../templates/index.html.j2
    dest: /var/www/html/index.html
    mode: "0644"
```

# 20. `import_playbook` et `import_tasks`

Le support montre comment découper une automatisation complexe.

```yaml
- import_playbook: install_php.yaml
- import_playbook: install_apache2.yaml
- import_playbook: install_wordpress.yaml
```

Pour des tâches :

```yaml
- import_tasks: tasks/common.yaml
```

Le but est d’éviter qu’un seul fichier devienne trop volumineux.

```text
site.yaml
├── install_php.yaml
├── install_apache2.yaml
└── install_wordpress.yaml
```

Cette transition prépare naturellement le chapitre suivant sur les **rôles**, qui apportent une structure standardisée plus complète.

# 21. Débogage du TP Apache/PostgreSQL

La version Multipass du support documente plusieurs difficultés réelles.

## 21.1 Apache ne démarre pas

Symptôme :

```text
Unable to start service apache2
Address already in use
could not bind to address 0.0.0.0:80
```

Diagnostic proposé dans le support :

```bash
ansible serveurweb1 -i inventaire.yaml -b \
  -m shell -a "ss -tlnp | grep ':80'"
```

Le support signale comme cause rencontrée dans son environnement la présence d’un autre serveur web occupant le port 80, notamment Nginx.

Vérification plus générale :

```bash
ansible serveurweb1 -i inventaire.yaml -b \
  -m shell -a "ss -ltnp | grep ':80' || true"
```

Puis vérifier le service identifié avant toute suppression.

## 21.2 Différence entre `command` et `shell`

Le support rappelle que les pipes comme `|` nécessitent le shell :

```bash
-m shell -a "ss -tlnp | grep ':80'"
```

plutôt qu’une commande ad hoc utilisant implicitement `command`.

## 21.3 PostgreSQL

Vérification :

```bash
ansible serveurdatabase1 -i inventaire.yaml \
  -m command -a "psql --version"
```

ou directement sur la machine :

```bash
sudo -i -u postgres
psql
```

# 22. Note importante sur les échecs dans le support Multipass

Le support indique d’abord qu’en cas d’échec d’une tâche, Ansible arrête l’exécution **sur l’hôte concerné** tout en poursuivant sur les autres hôtes.

Plus loin, la même version du support rapporte un incident où un échec Apache sur `serveurweb1` aurait empêché l’exécution du play PostgreSQL sur `serveurdatabase1`, pourtant distinct.

Ces deux formulations ne sont pas entièrement cohérentes entre elles. Le présent document conserve donc l’incident comme **retour d’expérience du TP**, sans le transformer en règle générale.

En cas de doute, vérifier concrètement :

```bash
ansible-playbook -i inventaire.yaml playbooks/datascientest-playbook.yaml -vv
```

et isoler si nécessaire :

```bash
ansible-playbook \
  -i inventaire.yaml \
  playbooks/datascientest-playbook.yaml \
  --limit serveurdatabase1
```

# 25. Du playbook au rôle

À ce stade, nous savons écrire :

```text
playbook
├── inventaire
├── variables
├── tasks
├── facts
├── conditions
├── boucles
├── tags
└── templates
```

Mais lorsque le projet grandit, un playbook monolithique devient difficile à maintenir.

Le chapitre suivant introduit :

```text
roles/
├── defaults/
├── handlers/
├── tasks/
├── templates/
├── files/
├── vars/
└── meta/
```

Le support DataScientest présente précisément cette transformation dans le module suivant.
