## 1. Objectifs du chapitre

Ce chapitre consolide le support DataScientest **« 3. Inventaire »** et son adaptation pratique à **Multipass / Ubuntu 24.04**.

À la fin de ce chapitre, l’apprenant doit être capable de :

- expliquer le rôle d’un inventaire Ansible ;
- distinguer inventaire statique et inventaire dynamique ;
- écrire un inventaire statique en INI ou YAML ;
- définir des hôtes, groupes, groupes enfants et variables ;
- comprendre les groupes implicites `all` et `ungrouped` ;
- utiliser des alias logiques pour les machines ;
- cibler un hôte, un groupe ou un groupe parent ;
- inspecter un inventaire avec `ansible-inventory` ;
- convertir la représentation d’un inventaire INI vers YAML ;
- préparer la séparation des variables avec `group_vars/` et `host_vars/` ;
- valider la connectivité et quelques modules par groupe et individuellement.

# 2. Pourquoi un inventaire ?

Ansible doit savoir **quelles machines piloter** et comment les organiser.

Sans inventaire, nous raisonnons surtout machine par machine :

```text
cible1
cible2
cible3
```

Avec un inventaire structuré, nous pouvons exprimer une organisation fonctionnelle :

```text
datascientest_app
├── dev
│   └── client-dev
├── test
│   └── client-test
└── prod
    └── client-prod
```

Le support DataScientest présente l’inventaire comme le fichier dans lequel sont décrits les hôtes et groupes d’hôtes sur lesquels s’appliquent commandes, modules et tâches de playbooks.

Un même système peut appartenir à plusieurs groupes. Les variables peuvent alors provenir de plusieurs niveaux de l’inventaire.

---

# 3. Inventaire par défaut et option `-i`

Le chemin d’inventaire par défaut présenté dans le cours est :

```text
/etc/ansible/hosts
```

Dans nos labs, nous utilisons des fichiers propres à chaque projet et nous les passons explicitement avec `-i` :

```bash
ansible all -i inventaire.ini -m ping
```

ou :

```bash
ansible all -i inventaire.yaml -m ping
```

Cette organisation garde le TP autonome et évite de dépendre d’un fichier système global.

# 4. Les deux types d’inventaires présentés dans le cours

Le cours distingue :

```text
Inventaire
├── statique
└── dynamique
```

## 4.1 Inventaire statique

Il est écrit directement sous forme de données, par exemple :

```text
INI
YAML
JSON
```

Le cours et le lab de ce chapitre se concentrent sur ce type d’inventaire.

## 4.2 Inventaire dynamique

Le support décrit les inventaires dynamiques comme des programmes capables de fournir les hôtes gérés à Ansible.

Le cours d’origine ne développe pas leur mise en œuvre : ils sont donc seulement introduits ici et ne font pas partie du lab 03.

# 5. Les composants d’un inventaire

Le support distingue plusieurs briques.

## 5.1 Hôtes

Un hôte représente une machine gérée.

```ini
client-dev ansible_host=<IP_CIBLE1>
```

Ici :

- `client-dev` est l’alias utilisé par Ansible ;
- `ansible_host` contient l’adresse réellement contactée.

L’alias nous permet de raisonner avec un nom métier sans renommer la VM Multipass.

```text
VM Multipass : cible1
        │
        ▼
Alias Ansible : client-dev
        │
        ▼
Adresse : <IP_CIBLE1>
```

---

## 5.2 Groupes

Un groupe rassemble plusieurs hôtes.

```ini
[dev]
client-dev ansible_host=<IP_CIBLE1>
```

Nous pouvons alors cibler le groupe entier :

```bash
ansible dev -i inventaire.ini -m ping
```

---

## 5.3 Variables d’hôte

Une variable peut être spécifique à un hôte.

```ini
client-dev ansible_host=<IP_CIBLE1>
```

`ansible_host` est ici propre à `client-dev`.

---

## 5.4 Variables de groupe

Le cas pratique DataScientest associe une variable `env` à chaque environnement :

```ini
[dev:vars]
env=dev

[test:vars]
env=test

[prod:vars]
env=prod
```

Cette variable pourra ensuite être réutilisée dans les playbooks.

---

## 5.5 Groupe parent / groupes enfants

Le cours utilise la notation `:children` pour créer un groupe de groupes.

```ini
[datascientest_app:children]
dev
test
prod
```

Le modèle devient :

```text
@datascientest_app
├── @dev
│   └── client-dev
├── @test
│   └── client-test
└── @prod
    └── client-prod
```

Nous pouvons désormais cibler les trois environnements via le groupe parent :

```bash
ansible datascientest_app -i inventaire.ini -m ping
```

---

## 5.6 Groupes implicites `all` et `ungrouped`

Le support rappelle deux groupes présents par défaut :

- `all` : tous les hôtes ;
- `ungrouped` : les hôtes qui ne sont dans aucun autre groupe explicite.

Dans notre cas pratique, le résultat souhaité est que `ungrouped` soit vide.

# 6. Paramètres de connexion présentés dans le cours

Le support introduit notamment :

| Paramètre | Rôle |
|---|---|
| `ansible_connection` | mode de connexion vers la cible |
| `ansible_port` | port de connexion SSH |
| `ansible_user` | utilisateur distant |
| `ansible_ssh_pass` | mot de passe SSH |
| `ansible_ssh_private_key_file` | chemin de la clé privée SSH |
| `ansible_become_pass` | mot de passe pour l’élévation de privilèges |

Dans notre adaptation Multipass, le lab précédent a mis en place une authentification par clé SSH. Nous privilégions donc :

```ini
ansible_user=datascientest
ansible_ssh_private_key_file=~/.ssh/id_rsa
```

Les mots de passe pédagogiques présents dans les supports sources ne sont pas recopiés dans le dépôt public.

# 7. Cas pratique DataScientest adapté à Multipass

L’objectif du TP est de disposer de :

```text
ansible-master
│
├── cible1 → client-dev  → groupe dev
├── cible2 → client-test → groupe test
└── cible3 → client-prod → groupe prod
```

avec :

```text
datascientest_app
├── dev  (env=dev)
├── test (env=test)
└── prod (env=prod)
```

Les adresses IP ne sont pas figées dans le dépôt : elles doivent être récupérées avec :

```bash
multipass list
```

# 8. Inventaire INI

Créez `inventaire.ini` :

```ini
[dev]
client-dev ansible_host=<IP_CIBLE1>

[test]
client-test ansible_host=<IP_CIBLE2>

[prod]
client-prod ansible_host=<IP_CIBLE3>

[dev:vars]
env=dev

[test:vars]
env=test

[prod:vars]
env=prod

[datascientest_app:children]
dev
test
prod

[all:vars]
ansible_user=datascientest
ansible_ssh_private_key_file=~/.ssh/id_rsa
```

Le support Multipass enrichi rapporte un incident observé dans son environnement lorsque la section `[all:vars]` était placée avant les groupes : certaines lignes avaient alors été interprétées comme des hôtes et apparaissaient sous `ungrouped`.

Dans ce dépôt, nous conservons donc **l’ordre qui a fonctionné dans le TP documenté**, avec `[all:vars]` à la fin.

> Cette remarque est conservée comme retour d’expérience du support adapté ; elle n’est pas généralisée ici au-delà de ce contexte de lab.

# 9. Inspecter l’inventaire

Avant toute action sur les machines, inspectez la structure.

## 9.1 Liste complète

```bash
ansible-inventory -i inventaire.ini --list
```

La sortie doit notamment montrer :

```text
client-dev  → env=dev
client-test → env=test
client-prod → env=prod
```

## 9.2 Vue graphique

```bash
ansible-inventory -i inventaire.ini --graph
```

Résultat attendu :

```text
@all:
  |--@datascientest_app:
  |  |--@dev:
  |  |  |--client-dev
  |  |--@test:
  |  |  |--client-test
  |  |--@prod:
  |  |  |--client-prod
  |--@ungrouped:
```

Cette commande est particulièrement utile pour vérifier visuellement qu’un hôte n’a pas été placé dans le mauvais groupe.

# 10. Représentation YAML

Le support fait ensuite produire une représentation YAML à partir de l’inventaire INI :

```bash
ansible-inventory -i inventaire.ini -y --list > inventaire.generated.yaml
```

Une structure équivalente ressemble à :

```yaml
all:
  children:
    datascientest_app:
      children:
        dev:
          hosts:
            client-dev:
              ansible_host: <IP_CIBLE1>
              env: dev
        test:
          hosts:
            client-test:
              ansible_host: <IP_CIBLE2>
              env: test
        prod:
          hosts:
            client-prod:
              ansible_host: <IP_CIBLE3>
              env: prod
```

Le cours présente YAML comme une représentation plus lisible de la hiérarchie de groupes.

# 11. `ansible.cfg` du lab

Le support Multipass utilise un fichier projet minimal :

```ini
[defaults]
host_key_checking = False
interpreter_python = auto_silent
```

Dans notre parcours, cette configuration est limitée au lab local jetable.

Elle doit être placée dans le répertoire depuis lequel les commandes sont exécutées.

# 12. Validation de la connectivité

Test global :

```bash
ansible all -i inventaire.ini -m ping
```

Test du groupe `dev` :

```bash
ansible dev -i inventaire.ini -m ping
```

Test d’un seul hôte :

```bash
ansible client-prod -i inventaire.ini -m ping
```

Résultat attendu pour chaque cible :

```text
SUCCESS
ping: pong
```

# 13. Valider le ciblage avec les modules du chapitre précédent

Le cas pratique demande de tester `copy`, `ping`, `apt` et `setup` à la fois par groupe et individuellement.

## 13.1 `setup`

```bash
ansible all -i inventaire.ini -m setup -a "filter=ansible_memtotal_mb"
```

Par groupe :

```bash
ansible prod -i inventaire.ini -m setup -a "filter=ansible_virtualization_type"
```

## 13.2 `copy`

```bash
echo "Inventaire Ansible DataScientest" > datascientest.txt
ansible all -i inventaire.ini \
  -m ansible.builtin.copy \
  -a "src=datascientest.txt dest=/home/datascientest/datascientest.txt"
```

## 13.3 `apt`

Sur le groupe `dev` :

```bash
ansible dev -i inventaire.ini -b \
  -m ansible.builtin.apt \
  -a "name=curl state=present update_cache=yes"
```

# 14. Variables dans `group_vars/` et `host_vars/`

Le support du chapitre Playbook poursuit ensuite l’organisation de l’inventaire en séparant les variables dans :

```text
group_vars/
host_vars/
```

Nous introduisons cette organisation ici comme **préparation au chapitre suivant**.

## 14.1 Variables communes

```yaml
# group_vars/all.yml
ansible_user: datascientest
ansible_ssh_private_key_file: ~/.ssh/id_rsa
```

## 14.2 Variable par groupe

```yaml
# group_vars/dev.yml
env: dev
```

```yaml
# group_vars/test.yml
env: test
```

```yaml
# group_vars/prod.yml
env: prod
```

## 14.3 Variable propre à un hôte

```yaml
# host_vars/client-dev.yml
ansible_host: <IP_CIBLE1>
```

Cette séparation permet d’obtenir un fichier d’inventaire essentiellement structurel :

```yaml
all:
  children:
    datascientest_app:
      children:
        dev:
          hosts:
            client-dev:
        test:
          hosts:
            client-test:
        prod:
          hosts:
            client-prod:
```

Nous approfondirons l’usage des variables dans `191.04_ANSIBLE_PLAYBOOKS.md`.

# 16. Débogage de l’inventaire

## 16.1 Un hôte apparaît dans `ungrouped`

Commencez par :

```bash
ansible-inventory -i inventaire.ini --graph
```

Puis inspectez le fichier INI :

- nom de section ;
- syntaxe `[groupe]` ;
- syntaxe `[parent:children]` ;
- ligne d’hôte ;
- position et contenu des sections de variables dans le lab reproduit.

---

## 16.2 `Could not resolve hostname ...`

Si une ligne censée être une variable est interprétée comme un hostname, inspectez immédiatement :

```bash
ansible-inventory -i inventaire.ini --list
ansible-inventory -i inventaire.ini --graph
```

Dans le retour d’expérience Multipass fourni, cette vérification a permis d’identifier des lignes de variables apparaissant comme hôtes.

---

## 16.3 `UNREACHABLE`

L’inventaire peut être syntaxiquement correct mais la connexion SSH incorrecte.

Vérifiez :

```bash
ssh datascientest@<IP_CIBLE>
```

puis :

```bash
ansible client-dev -i inventaire.ini -m ping -vvvv
```

Points à contrôler :

```text
IP
alias
ansible_user
clé SSH
port
VM démarrée
```

---

## 16.4 Le bon `ansible.cfg` n’est pas chargé

Vérifiez :

```bash
ansible --version
```

et observez la ligne `config file`.

Dans le lab Multipass, les commandes sont lancées depuis le répertoire contenant le `ansible.cfg` du projet.

# 20. À retenir

L’inventaire transforme une liste d’adresses techniques en une **topologie exploitable par Ansible**.

Le point important n’est pas seulement :

```text
« quelles IP ? »
```

mais :

```text
« quels hôtes ? »
« quels groupes ? »
« quelles relations ? »
« quelles variables ? »
« quelle cible pour cette automatisation ? »
```

Dans notre parcours :

```text
Lab 01 → machines disponibles
Lab 02 → modules exécutés sur des cibles
Lab 03 → cibles organisées en inventaire
Lab 04 → plusieurs tâches orchestrées par playbooks
```

Le prochain chapitre est donc :

```text
191.04_ANSIBLE_PLAYBOOKS.md
```
