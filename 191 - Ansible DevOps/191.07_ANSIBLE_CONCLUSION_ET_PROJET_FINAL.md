---

# 2. Le besoin métier de l’évaluation

Le scénario fourni est celui d’une startup e-commerce souhaitant créer et déployer un nouveau site web.

La solution de référence demandée par le support est :

```text
Prestashop
    │
    ├── serveur web
    │
    └── communication
             │
             ▼
           MySQL
```

Le travail doit automatiser ce déploiement au moyen de **deux rôles distincts** :

- un rôle pour Prestashop ;
- un rôle pour MySQL.

Le support exige explicitement que le serveur web puisse communiquer avec la base de données.

Il autorise aussi une alternative telle que Magento ou WordPress si la solution répond au besoin exprimé.

---

# 3. Livrables demandés

Le rendu attendu par l’évaluation est une archive `.zip` contenant :

1. deux arborescences de rôles correspondant aux besoins ;
2. le playbook qui orchestre leur exécution ;
3. les logs des résultats de tests dans un fichier `.txt` ;
4. des scripts fonctionnels quel que soit l’environnement utilisé.

Le projet final de ce repository conservera ces exigences comme critères de sortie.

---

# 4. Architecture pédagogique minimale

Le support recommande un rôle par machine et suggère de commencer par l’inventaire.

La topologie minimale devient donc :

```text
                    CONTROL NODE
                      Ansible
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
      serveur web                serveur DB
      Prestashop                 MySQL
      rôle web                   rôle mysql
        :80                        :3306
             │                       ▲
             └──── connexion SQL ────┘
```

Le port HTTP indiqué dans l’énoncé est `80`. Le port MySQL indiqué est `3306`.

---

# 5. Distinguer l’énoncé de la mise en œuvre de référence

Le support contient aussi un conseil de démarrage demandant de créer un utilisateur `root` pour permettre la connexion à la base de données.

Dans ce repository, nous conservons cette consigne dans le document d’énoncé pour respecter la source.

La documentation de mise en œuvre de référence distinguera toutefois :

```text
EXIGENCE SOURCE
    ↓
ce que demande le support

REFERENCE D’IMPLEMENTATION
    ↓
comment rendre la solution testable,
portable et plus sûre
```

Ainsi, les écarts éventuels sont documentés au lieu d’être introduits silencieusement.

# 6. De l’exercice guidé au projet final

Le Lab 05 installait WordPress et MySQL sur une seule machine afin d’apprendre les rôles.

L’évaluation introduit une rupture importante :

```text
LAB 05
une machine
└── rôle wordpress
    ├── web
    └── mysql

              ↓ évaluation

PROJET FINAL
serveur web              serveur database
└── rôle web              └── rôle mysql
```

Cette séparation apporte un vrai cas d’orchestration multi-hôtes.

---

# 7. Ce que doit prouver la solution

Une solution considérée comme prête pour l’évaluation doit démontrer au minimum :

```text
inventaire valide
      ↓
SSH OK
      ↓
rôle DB exécutable
      ↓
rôle Web exécutable
      ↓
connexion web → DB
      ↓
HTTP :80 accessible
      ↓
relance Ansible cohérente
      ↓
logs de tests exportés
      ↓
archive ZIP reproductible
```
