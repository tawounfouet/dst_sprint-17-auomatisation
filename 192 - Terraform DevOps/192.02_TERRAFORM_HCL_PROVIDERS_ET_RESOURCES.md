# 192.02 — Terraform : HCL, providers et ressources

> Sprint 17 — Automatisation  
> Module : Terraform DevOps  
> Durée indicative DataScientest : 1 h

## 1. Objectifs pédagogiques

Ce chapitre présente le langage **HCL**, les **providers**, les commandes principales de Terraform et la notion de **resource**. Il introduit également deux cas pratiques : le déploiement de ressources Kubernetes/Helm et la création d’une instance EC2 sur AWS.

À l’issue de ce chapitre, on doit être capable de :

- lire et écrire une configuration HCL ;
- distinguer arguments, blocs et identifiants ;
- déclarer et versionner un provider ;
- utiliser les commandes principales de Terraform ;
- créer des ressources Kubernetes et AWS ;
- comprendre le rôle de Helm dans un cluster Kubernetes ;
- appliquer puis détruire une infrastructure Terraform.

---

## 2. Le langage HCL

Terraform utilise le **HashiCorp Configuration Language (HCL)**. Le support le présente comme un langage :

- lisible ;
- concis ;
- flexible sur les espaces et l’indentation ;
- adapté à la structuration d’un projet en plusieurs fichiers `.tf`.

Terraform peut également utiliser JSON, mais HCL reste la syntaxe privilégiée dans le cours.

---

## 3. Arguments et blocs

### 3.1 Argument

Un argument associe un nom à une valeur :

```hcl
name = "Datascientest-namespace"
```

Structure :

```text
IDENTIFIANT = EXPRESSION
```

### 3.2 Bloc

Un bloc structure la configuration :

```hcl
resource "kubernetes_namespace" "datascientest_namespace" {
  metadata {
    labels = {
      app = "Datascientest-namespace"
    }
    name = "Datascientest-namespace"
  }
}
```

Structure générale :

```text
TYPE_DE_BLOC "LABEL_1" "LABEL_2" {
  argument = expression
}
```

Les blocs peuvent contenir d’autres blocs imbriqués.

---

## 4. Identifiants et commentaires

Les identifiants peuvent contenir des lettres, chiffres, `_` et `-`, mais ne doivent pas commencer par un chiffre.

Commentaires disponibles :

```hcl
# commentaire recommandé
// commentaire alternatif
/* commentaire
   multiligne */
```

Le style `#` est recommandé dans le support.

## 5. Les providers Terraform

Un **provider** est un plugin permettant à Terraform d’interagir avec une API.

Exemples cités dans le cours :

- AWS ;
- Azure ;
- VMware vSphere ;
- Active Directory ;
- Kubernetes ;
- Docker ;
- OpenStack ;
- DigitalOcean ;
- OVH ;
- GitLab ;
- MySQL.

Exemple AWS :

```hcl
provider "aws" {
  region = "eu-west-3"
}
```

Exemple Kubernetes :

```hcl
provider "kubernetes" {
  config_path    = "~/.kube/config"
  config_context = "microservices"
}
```

---

## 6. Versionner les providers

Le cours recommande de déclarer les contraintes de version dans `required_providers` :

```hcl
terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.9.0"
    }
  }
}
```

Exemples de contraintes :

```text
<= 2.9.0
>= 2.9.0
>= 1.2.0, < 2.0.0
~> 1.0.4
```

L’opérateur `~>` autorise l’incrémentation du composant de version le plus à droite selon la contrainte donnée.

## 7. Initialiser un projet

```bash
terraform init
```

Cette commande :

- initialise le backend ;
- télécharge les plugins nécessaires ;
- crée le fichier `.terraform.lock.hcl` ;
- prépare le répertoire de travail.

Pour mettre à niveau les providers selon de nouvelles contraintes :

```bash
terraform init -upgrade
```

## 9. Les ressources Terraform

Une **resource** représente une composante d’infrastructure créée ou gérée par Terraform.

Exemples :

### Kubernetes

- pods ;
- deployments ;
- services ;
- ingress ;
- statefulsets.

### AWS

- EC2 ;
- security groups ;
- load balancers ;
- bases de données.

Syntaxe :

```hcl
resource "TYPE" "NOM_LOGIQUE" {
  # configuration
}
```

## 10. Cas pratique Kubernetes avec k3s

Le support utilise **k3s** comme cluster Kubernetes léger.

Installation :

```bash
curl -sfL https://get.k3s.io | sh -s - --write-kubeconfig-mode 644
```

Vérification :

```bash
kubectl version
```

```bash
mkdir -p ~/.kube
kubectl config view --raw > ~/.kube/config
```

## 11. Déploiement WordPress + MySQL via provider Kubernetes

Le cours construit une application composée de :

- secrets Kubernetes ;
- un deployment WordPress ;
- un service WordPress ;
- un deployment MySQL ;
- un service MySQL.

Exemple de provider :

```hcl
provider "kubernetes" {
  config_path = "~/.kube/config"
}

terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.9.0"
    }
  }
}
```

Le cours introduit également les **locals** pour centraliser des labels :

```hcl
locals {
  datascientest_wordpress = {
    App  = "datascientest-wordpress"
    Tier = "frontend"
  }
}
```

Déploiement :

```bash
terraform init
terraform plan
terraform apply -auto-approve
kubectl get all
```

Nettoyage :

```bash
terraform destroy -auto-approve
```

## 12. Helm dans Terraform

Le support présente **Helm** comme un gestionnaire de packages Kubernetes basé sur des charts.

Le provider Helm permet à Terraform d’installer ces charts.

Exemple :

```hcl
provider "helm" {
  kubernetes = {
    config_path = "~/.kube/config"
  }
}

resource "helm_release" "mysql" {
  name      = "mysql"
  namespace = "wordpress"
  chart     = "${path.module}/mysql-chart"

  values = [
    file("${path.module}/mysql-chart/values.yaml")
  ]

  create_namespace = true
}
```

Une seconde release WordPress peut dépendre de MySQL :

```hcl
depends_on = [
  helm_release.mysql
]
```

## 13. Cas pratique AWS : première instance EC2

Le support crée un projet AWS avec un provider versionné :

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "eu-west-3"
}
```

Exemple d’instance :

```hcl
resource "aws_instance" "datascientest_instance" {
  ami           = "ami-03601e822a943105f"
  instance_type = "t3.micro"
  key_name      = "votre_prenom-datascientest_keypair"

  tags = {
    Name = "datascientest"
  }
}
```

Workflow :

```bash
terraform init
terraform plan
terraform apply --auto-approve
aws ec2 describe-instances
terraform destroy --auto-approve
```

> Les identifiants AWS présents dans les supports d’origine ne sont volontairement pas reproduits ici. Les credentials doivent être injectés de manière sécurisée.

## 15. Points clés à retenir

1. HCL structure les configurations Terraform en arguments et blocs.
2. Un provider connecte Terraform à une API externe.
3. Les versions de providers doivent être contraintes explicitement.
4. Une resource représente un objet d’infrastructure géré par Terraform.
5. `terraform init` prépare le répertoire de travail.
6. `terraform plan` prévisualise les changements.
7. `terraform apply` applique la configuration.
8. `terraform destroy` supprime les ressources gérées.
9. Terraform peut gérer aussi bien AWS que Kubernetes ou Helm.
