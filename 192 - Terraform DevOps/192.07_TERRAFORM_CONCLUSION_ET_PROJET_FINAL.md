# 192.07 — Terraform : Conclusion et projet final

> Sprint 17 — Automatisation  
> Module : Terraform DevOps  
> Durée indicative DataScientest : 5 h  
> Niveau : Normal

## 1. Objectif du projet final

Le projet final valide les compétences acquises dans le module Terraform en demandant de **concevoir, modulariser, déployer et tester une architecture AWS complète pour héberger un site WordPress**.

Le contexte fourni est celui d’un ingénieur DevOps chargé d’automatiser le déploiement de l’infrastructure d’une entreprise.

Le livrable attendu doit être :

- reproductible ;
- réutilisable ;
- lisible ;
- modulaire ;
- déployable ;
- sans secrets codés en dur ;
- conforme au besoin fonctionnel et technique demandé.

---

## 2. Architecture demandée

La région AWS imposée est :

```text
eu-west-3 — Paris
```

L’architecture doit comprendre au minimum :

- une instance EC2 `t3.micro` pour héberger WordPress ;
- une récupération dynamique de l’AMI ;
- une récupération dynamique des Availability Zones ;
- une base de données via `aws_db_instance` ;
- un déploiement de la base dans deux Availability Zones distinctes ;
- un volume EBS supplémentaire de 10 Go ;
- un accès HTTP sur le port 80 ;
- en bonus, un accès HTTPS sur le port 443 avec TLS ;
- une organisation du code en modules Terraform.

---

## 4. Contraintes techniques

### 4.1 Région

```hcl
variable "region" {
  type    = string
  default = "eu-west-3"
}
```

### 4.2 Instance EC2

Le support demande une instance :

```text
Instance type : t3.micro
Usage         : serveur web WordPress
```

L’AMI doit être récupérée dynamiquement via une data source.

Exemple :

```hcl
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*"]
  }
}
```

Puis :

```hcl
ami = data.aws_ami.amazon_linux.id
```

---

## 5. Availability Zones dynamiques

Le support demande également de récupérer automatiquement les Availability Zones compatibles.

Exemple :

```hcl
data "aws_availability_zones" "available" {}
```

Puis :

```hcl
data.aws_availability_zones.available.names
```

---

## 6. Base de données RDS

La ressource imposée est :

```text
aws_db_instance
```

Type demandé :

```text
db.t3.micro
```

La base doit être déployée dans une architecture couvrant deux Availability Zones distinctes de la région `eu-west-3`.

Le module RDS devra exposer les informations nécessaires au reste de l’infrastructure, par exemple :

- endpoint ;
- port ;
- nom de la base ;
- autres outputs nécessaires à WordPress.

Les mots de passe ne doivent jamais être codés en dur.

---

## 7. Volume EBS

Le projet impose un disque EBS supplémentaire de :

```text
10 Go
```

Contrainte essentielle :

```text
EC2 et EBS
     ↓
Même Availability Zone
```

Exemple de structure :

```hcl
resource "aws_ebs_volume" "wordpress_data" {
  availability_zone = var.availability_zone
  size              = 10
}
```

Puis attachement :

```hcl
resource "aws_volume_attachment" "wordpress_data_attachment" {
  device_name = "/dev/sdh"
  volume_id   = aws_ebs_volume.wordpress_data.id
  instance_id = var.instance_id
}
```

---

## 8. Accès HTTP

Le serveur web doit être accessible depuis un navigateur sur le port :

```text
80/TCP
```

Exemple de règle :

```hcl
ingress {
  from_port   = 80
  to_port     = 80
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
}
```

## 9. Bonus HTTPS

Le support propose comme bonus :

```text
HTTPS
Port 443
TLS
```

Le détail de l’implémentation TLS n’est pas imposé dans le support ; seule la configuration d’un accès sécurisé HTTPS est explicitement demandée comme bonus.

## 10. Installation de WordPress

Le projet final réutilise la logique vue dans le chapitre précédent avec un script :

```text
install_wordpress.sh
```

Ce script est injecté au démarrage via `user_data`.

Exemple :

```hcl
user_data = file("install_wordpress.sh")
```

Le script peut prendre en charge :

- installation du serveur web ;
- installation de PHP ;
- installation/configuration de WordPress ;
- configuration nécessaire à la connexion vers la base de données.

## 12. Responsabilités des modules

### `networking`

Responsable de :

- VPC ;
- subnets ;
- Availability Zones ;
- Security Groups ;
- routage nécessaire.

### `ec2`

Responsable de :

- instance WordPress ;
- AMI ;
- type d’instance ;
- réseau ;
- `user_data` ;
- outputs de l’instance.

### `rds`

Responsable de :

- instance de base de données ;
- paramètres RDS ;
- subnet group si nécessaire ;
- informations de connexion ;
- outputs.

### `ebs`

Responsable de :

- volume 10 Go ;
- Availability Zone ;
- attachement à l’EC2.

## 13. Gestion des secrets

Condition de validation explicite :

> Aucun mot de passe ne doit apparaître en dur dans le code.

Les valeurs sensibles doivent être passées via des variables appropriées plutôt que directement intégrées aux fichiers Terraform.

Exemple :

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}
```

Le fichier `terraform.tfvars` contenant de vraies valeurs sensibles ne doit pas être partagé publiquement.

On peut prévoir un exemple :

```text
terraform.tfvars.example
```

sans valeurs réelles.

## 15. Workflow de validation recommandé

Le projet doit être testé avant livraison.

Workflow cohérent avec les commandes vues dans le cours :

```bash
terraform fmt
terraform init
terraform validate
terraform plan
terraform apply
```

Puis validation fonctionnelle :

```text
EC2 disponible
      ↓
WordPress installé
      ↓
HTTP accessible
      ↓
RDS disponible
      ↓
EBS attaché
      ↓
Architecture conforme
```

Enfin :

```bash
terraform destroy --auto-approve
```

---

## 16. Condition essentielle de nettoyage

Le support impose de supprimer les ressources créées avec Terraform **en utilisant Terraform**.

Commande :

```bash
terraform destroy --auto-approve
```

Cela garantit que le state et l’infrastructure restent cohérents.
