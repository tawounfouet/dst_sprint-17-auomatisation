# 192.07 — Retour d'expérience

## Statut

Ce retour d'expérience porte sur la **conception et l'implémentation du code Terraform**. Il ne doit pas être confondu avec un retour d'exécution AWS réel tant que la qualification end-to-end n'a pas été réalisée.

## Principaux enseignements

### 1. Les dépendances deviennent plus claires avec les modules

Le découpage `networking → rds/ec2 → ebs` rend les responsabilités explicites et évite un fichier `main.tf` monolithique.

### 2. Les outputs constituent l'interface des modules

Le projet repose sur des échanges simples :

```text
networking.public_subnet_ids
networking.db_security_group_id
rds.endpoint
rds.master_user_secret_arn
ec2.instance_id
ec2.availability_zone
```

Cette approche montre concrètement comment les modules Terraform composent une infrastructure.

### 3. Les dépendances implicites sont préférables

La plupart des ordres de création sont déduits des références entre ressources. Un seul `depends_on` explicite est conservé dans le module EC2 pour éviter que le bootstrap tente de lire le secret avant l'attachement effectif de la policy IAM.

### 4. « Pas de mot de passe en dur » peut être traité plus proprement qu'avec une simple variable

Le support pédagogique propose des variables. L'implémentation utilise le mot de passe maître géré par RDS/Secrets Manager afin d'éviter de placer ce secret dans `terraform.tfvars` ou dans Git.

### 5. L'EBS séparé crée une contrainte temporelle

Le volume EBS n'existe qu'après la création de l'EC2. Or `user_data` s'exécute au premier boot. Le script contient donc une fenêtre d'attente et détecte le second disque avant de le formater et de le monter sur les uploads WordPress.

### 6. Multi-AZ doit être distingué de « deux bases indépendantes »

Le besoin pédagogique de couvrir deux Availability Zones est implémenté avec un RDS Multi-AZ, c'est-à-dire une architecture de haute disponibilité gérée par AWS, et non deux bases WordPress concurrentes.

## Points à observer pendant le vrai `apply`

- disponibilité de `db.t3.micro` Multi-AZ dans le compte utilisé ;
- temps de provisioning RDS ;
- délai de propagation IAM/Secrets Manager ;
- détection effective du disque EBS par le bootstrap ;
- compatibilité des paquets Ubuntu du script ;
- résultat HTTP et installation WordPress ;
- coût du lab ;
- destruction complète.

## Prochaine étape

Après une qualification AWS réelle, ce document devra être complété avec :

- durée de `terraform apply` ;
- ressources réellement créées ;
- anomalies rencontrées ;
- corrections appliquées ;
- captures ou preuves ;
- durée de `terraform destroy` ;
- bilan de coût éventuel.
