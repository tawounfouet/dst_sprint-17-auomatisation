# 192.07 — Tests et validation du projet final

## Stratégie

La validation est séparée en deux niveaux :

1. **validation statique sans AWS** : formatage, initialisation, syntaxe Terraform, syntaxe Bash et contrôle basique de secrets ;
2. **qualification end-to-end AWS** : `plan`, `apply`, tests HTTP/HTTPS, contrôles RDS/EBS puis `destroy`.

## CI GitHub

Le workflow :

```text
.github/workflows/terraform-project-final.yml
```

exécute :

```bash
terraform fmt -check -recursive
terraform init -backend=false
terraform validate
bash -n modules/ec2/user_data.sh.tftpl
```

Il recherche également les motifs classiques de clés AWS `AKIA...` afin d'éviter la republication accidentelle des credentials présents dans les anciens supports de cours.

## Qualification AWS

Depuis `Projet_Final/wordpress-aws/` :

```bash
terraform plan -out=tfplan
terraform apply tfplan
```

Puis vérifier :

```bash
terraform output
curl -I "$(terraform output -raw wordpress_url)"
```

Pour HTTPS pédagogique :

```bash
curl -k -I "$(terraform output -raw wordpress_https_url)"
```

## Tests d'infrastructure

Les vérifications détaillées sont documentées dans :

```text
wordpress-aws/docs/VALIDATION.md
```

Elles couvrent :

- EC2 ;
- RDS Multi-AZ ;
- Security Groups ;
- Secrets Manager ;
- EBS ;
- WordPress ;
- bootstrap ;
- destruction complète.

## Critère de clôture

Le projet n'est qualifié end-to-end qu'après un `apply` AWS réel suivi d'un accès WordPress réussi et d'un `terraform destroy` réussi. La CI seule valide le code mais ne prouve pas la création réelle des ressources.
