# 192.07 — Spécifications du projet final Terraform

## Objectif

Construire avec Terraform une architecture AWS capable d'héberger WordPress dans la région Paris (`eu-west-3`) en appliquant les notions du module : HCL, providers, resources, data sources, variables, outputs, dépendances et modules.

## Exigences issues du support DataScientest

- une instance EC2 `t3.micro` pour WordPress ;
- AMI récupérée dynamiquement ;
- Availability Zones récupérées dynamiquement ;
- base de données via `aws_db_instance`, classe `db.t3.micro` ;
- base couvrant deux Availability Zones distinctes ;
- volume EBS additionnel de 10 Go ;
- EC2 et EBS dans la même Availability Zone ;
- accès HTTP sur le port 80 ;
- bonus HTTPS sur le port 443 avec TLS ;
- architecture segmentée en modules ;
- aucun mot de passe en dur ;
- code répétable, réutilisable et testable ;
- suppression de l'infrastructure avec Terraform.

## Structure cible

```text
modules/
├── networking/
├── ec2/
├── rds/
└── ebs/
```

## Implémentation retenue

Le code exécutable se trouve dans :

```text
Projet_Final/wordpress-aws/
```

La contrainte « deux Availability Zones pour la base » est implémentée avec un DB subnet group réparti sur deux AZ et un RDS MySQL avec `multi_az = true`.

Le mot de passe maître RDS est géré par AWS Secrets Manager via `manage_master_user_password = true`, ce qui évite de stocker un mot de passe dans le code ou dans `terraform.tfvars`.

## Hors périmètre

Le support n'impose pas ALB, Auto Scaling, Route 53, CloudFront, WAF ou monitoring. Ces briques ne sont donc pas nécessaires à la validation de ce projet final.
