# 192.07 — Qualification AWS réelle

> Projet final Terraform WordPress/AWS — Sprint 17 Automatisation

## 1. Objectif

Cette qualification ne se limite pas à `terraform validate`. Elle doit prouver que le projet peut réellement :

1. s'authentifier auprès d'AWS ;
2. interroger AWS pour les AMI et Availability Zones ;
3. produire un vrai `terraform plan` contre `eu-west-3` ;
4. créer l'infrastructure ;
5. vérifier les propriétés AWS attendues ;
6. rendre WordPress joignable en HTTP ;
7. détruire l'ensemble des ressources avec Terraform.

## 2. État actuel

### Validation statique

Le workflow `.github/workflows/terraform-project-final.yml` est vert et valide :

- `terraform fmt -check -recursive` ;
- `terraform init -backend=false` ;
- `terraform validate` ;
- syntaxe du bootstrap Bash ;
- absence de clé AWS de forme `AKIA...` committée dans le projet.

### Qualification AWS plan

Le workflow `.github/workflows/terraform-project-final-aws-plan.yml` a été ajouté pour exécuter un **vrai plan contre AWS**.

Il s'arrête volontairement avant tout appel AWS lorsqu'aucune authentification n'est configurée dans GitHub Actions.

État constaté au premier run exploitable :

```text
Require an AWS authentication method -> FAILURE
Configure AWS credentials          -> SKIPPED
aws sts get-caller-identity         -> SKIPPED
terraform plan                      -> SKIPPED
```

La cause est donc clairement identifiée : **aucune identité AWS n'est encore fournie à GitHub Actions**.

Ce n'est pas un échec du code Terraform ; c'est le verrou d'authentification préalable à la qualification réelle.

## 3. Authentification supportée

Deux méthodes sont prévues.

### Option A — GitHub OIDC — recommandée

Créer un rôle IAM assumable par GitHub Actions puis définir dans le dépôt le secret :

```text
AWS_ROLE_ARN
```

Aucune clé AWS longue durée n'est alors stockée dans GitHub.

### Option B — Clés d'accès temporaires ou dédiées au lab

Définir :

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

Et, si les identifiants sont temporaires :

```text
AWS_SESSION_TOKEN
```

Ne jamais copier dans le dépôt les credentials présents dans les supports pédagogiques DataScientest.

## 4. Qualification plan

Une fois l'authentification configurée, le workflow :

```text
Terraform Project Final - AWS Plan
```

exécute :

```text
aws sts get-caller-identity
terraform fmt -check -diff -recursive
terraform init
terraform validate
terraform plan -out=tfplan
terraform show tfplan
```

Le plan complet est conservé pendant 7 jours comme artifact GitHub Actions.

Ce gate doit être vert avant d'exécuter le déploiement end-to-end.

## 5. Qualification end-to-end

Le workflow :

```text
Terraform Project Final - AWS E2E Qualification
```

est uniquement déclenchable manuellement.

Pour éviter une création accidentelle de ressources payantes, il exige la chaîne :

```text
QUALIFY
```

Le workflow réalise ensuite :

```text
AWS authentication
      ↓
terraform plan
      ↓
terraform apply
      ↓
AWS property checks
      ↓
WordPress HTTP smoke test
      ↓
qualification evidence
      ↓
terraform destroy
```

## 6. Vérifications AWS réelles

Après `apply`, le workflow vérifie via AWS CLI :

### EC2

- instance réellement créée ;
- Availability Zone récupérée depuis AWS.

### EBS

- volume réellement créé ;
- volume et EC2 dans la **même Availability Zone**.

### RDS

- instance réellement créée ;
- propriété `MultiAZ = true`.

### WordPress

Le DNS public Terraform est interrogé pendant une fenêtre maximale de 10 minutes.

La qualification HTTP est acceptée si le serveur répond :

```text
HTTP 200
```

ou :

```text
HTTP 302
```

Ce test valide simultanément une partie importante de la chaîne :

```text
EC2
 ↓
user_data / cloud-init
 ↓
Apache + PHP
 ↓
WordPress
 ↓
Security Group HTTP
 ↓
route publique + Internet Gateway
```

## 7. Preuves générées

Le workflow produit un artifact :

```text
terraform-project-final-aws-e2e-evidence
```

contenant selon l'avancement :

```text
qualification-plan.txt
qualification-outputs.json
qualification-outputs.txt
qualification-aws-properties.txt
qualification-http.txt
ec2-console-output.txt
qualification-report.md
```

## 8. Destruction obligatoire

Le dernier step est exécuté avec :

```bash
terraform destroy -input=false -auto-approve -no-color
```

Il utilise le même state local que l'`apply`, car l'ensemble du cycle de qualification est effectué dans **un seul job GitHub Actions**.

Si le `destroy` échoue, le workflow remonte explicitement une erreur demandant une vérification immédiate des ressources résiduelles dans AWS.

## 9. Coûts

La qualification E2E crée temporairement des ressources AWS, notamment :

- EC2 ;
- RDS Multi-AZ ;
- EBS ;
- VPC et composants réseau ;
- potentiellement Secrets Manager selon le mode RDS utilisé.

Elle peut donc générer des coûts, même si les ressources sont détruites à la fin du run.

## 10. Critères de qualification finale

Le projet ne sera déclaré **AWS E2E qualifié** qu'après obtention des preuves suivantes :

```text
[ ] aws sts get-caller-identity OK
[ ] terraform plan réel OK
[ ] terraform apply OK
[ ] EC2 créée
[ ] EBS 10 GiB créée
[ ] EC2 AZ == EBS AZ
[ ] RDS créée
[ ] RDS Multi-AZ == true
[ ] WordPress HTTP joignable
[ ] artifact de preuves généré
[ ] terraform destroy OK
[ ] aucune ressource résiduelle connue
```
