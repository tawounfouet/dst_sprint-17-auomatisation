# 192.01 — Terraform : Introduction et installation

> Sprint 17 — Automatisation  
> Module : Terraform DevOps  
> Durée indicative DataScientest : 1 h  
> Niveau : Normal

## 1. Objectifs pédagogiques

Ce chapitre introduit **Terraform** et les principes de l’**Infrastructure as Code (IaC)**. L’objectif est de comprendre pourquoi l’infrastructure peut être décrite, versionnée et déployée sous forme de code, puis d’installer Terraform sur un environnement Linux.

À l’issue de ce chapitre, on doit être capable de :

- expliquer le principe de l’Infrastructure as Code ;
- identifier les bénéfices de l’IaC dans un contexte DevOps ;
- décrire le fonctionnement général de Terraform ;
- distinguer **Terraform Core** des **providers** ;
- comprendre le caractère déclaratif et multi-provider de Terraform ;
- installer Terraform sur Ubuntu/Debian ;
- vérifier que l’installation est opérationnelle.

---

## 2. Qu’est-ce que l’Infrastructure as Code ?

L’**Infrastructure as Code** consiste à créer et gérer des systèmes informatiques à partir de fichiers de configuration ou de code, plutôt qu’en réalisant manuellement les opérations depuis une console d’administration.

Les composants d’infrastructure — par exemple les serveurs, réseaux, machines virtuelles, load balancers, espaces de stockage ou bases de données — sont décrits sous une forme reproductible et versionnable.

L’IaC permet ainsi de passer d’une logique :

```text
Actions manuelles dans une console
        ↓
Infrastructure difficile à reproduire
```

à une logique :

```text
Configuration versionnée
        ↓
Outil IaC
        ↓
Infrastructure reproductible
```

Terraform s’inscrit dans cette approche en décrivant l’**état final souhaité** de l’infrastructure.

---

## 3. Pourquoi utiliser l’Infrastructure as Code ?

### 3.1 Rapidité et efficacité

L’IaC permet d’automatiser la création des ressources nécessaires au déploiement d’une application :

- réseaux ;
- serveurs ;
- bases de données ;
- comptes ou accès ;
- ressources de calcul ;
- services cloud.

La création et la suppression de ressources deviennent beaucoup plus rapides qu’avec une approche exclusivement manuelle.

### 3.2 Cohérence des environnements

Une même configuration peut être réutilisée pour créer plusieurs environnements proches ou identiques :

```text
Configuration IaC
   ├── DEV
   ├── TEST
   ├── RECETTE
   └── PROD
```

Cette reproductibilité réduit les écarts entre environnements et facilite les tests dans des conditions proches de la production.

### 3.3 Autonomie des équipes

Les développeurs et équipes DevOps peuvent créer plus facilement des environnements conformes aux besoins du projet sans devoir reconstruire manuellement chaque ressource.

Cela réduit :

- les délais de mise à disposition ;
- les manipulations répétitives ;
- le risque d’erreurs humaines ;
- la complexité des procédures de déploiement.

### 3.4 Versionnement et traçabilité

Comme l’infrastructure est décrite dans des fichiers, elle peut être gérée avec Git.

On peut alors suivre :

- **quoi** a été modifié ;
- **quand** ;
- **par qui** ;
- **pourquoi** ;
- quelle version de la configuration correspond à un environnement donné.

### 3.5 Idempotence

L’idempotence signifie qu’une configuration décrit un **état cible**. L’exécution répétée d’un déploiement ne doit pas créer arbitrairement de nouvelles différences : l’outil doit rapprocher l’infrastructure réelle de l’état déclaré.

L’objectif est donc :

```text
État déclaré
      ↓
Comparaison avec l’existant
      ↓
Création / modification / suppression nécessaires
      ↓
État réel conforme à l’état attendu
```

### 3.6 Bénéfices principaux

L’approche IaC permet notamment de :

- réduire les sources d’erreurs ;
- tester plus tôt ;
- redéployer de façon fiable ;
- standardiser les environnements ;
- accélérer les déploiements ;
- faciliter la collaboration ;
- tracer l’évolution de l’infrastructure.

## 4. Qu’est-ce que Terraform ?

Terraform est un outil d’Infrastructure as Code permettant de **créer, modifier et versionner une infrastructure** de manière déclarative.

Au lieu d’écrire une suite impérative d’instructions comme :

```text
1. Créer un réseau
2. Créer un sous-réseau
3. Créer une VM
4. Attacher la VM au réseau
```

on décrit les ressources souhaitées et leurs relations. Terraform détermine ensuite les opérations nécessaires pour atteindre cet état.

Terraform peut gérer, selon les providers utilisés :

- instances de calcul ;
- réseaux ;
- stockage ;
- bases de données ;
- ressources Kubernetes ;
- services SaaS ;
- nombreux autres composants d’infrastructure.

---

## 5. Approche déclarative

Terraform utilise une approche **déclarative** : la configuration décrit principalement **ce que l’on veut obtenir**, plutôt que l’ensemble exact des étapes procédurales permettant de l’obtenir.

```text
Code Terraform
      ↓
État souhaité
      ↓
Terraform calcule les changements
      ↓
Infrastructure cible
```

Cette approche rend la configuration plus lisible et facilite la gestion des évolutions.

---

## 6. Architecture générale de Terraform

Le support DataScientest distingue deux éléments essentiels :

### 6.1 Terraform Core

Le moteur Terraform :

- lit les fichiers de configuration ;
- construit le graphe de dépendances ;
- compare la configuration à l’état connu ;
- calcule les changements nécessaires ;
- orchestre les opérations à effectuer.

### 6.2 Les providers

Un **provider** est le composant qui permet à Terraform de communiquer avec une plateforme ou un service via son API.

Exemples :

- AWS ;
- Microsoft Azure ;
- Google Cloud ;
- Kubernetes ;
- Docker ;
- GitLab ;
- DigitalOcean ;
- OpenStack ;
- OVH.

Le workflow peut être résumé ainsi :

```text
Utilisateur
    ↓
Fichiers Terraform (*.tf)
    ↓
Terraform Core
    ↓
Provider
    ↓
API de la plateforme
    ↓
Infrastructure
```

---

## 7. Terraform et le multi-cloud

Terraform est présenté dans le cours comme un outil **cloud agnostic** : il peut conserver un workflow similaire tout en utilisant différents providers.

```text
                Terraform
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
       AWS        Azure        GCP
```

Cela ne signifie pas que les ressources sont identiques d’un cloud à l’autre : chaque provider expose ses propres types de ressources et paramètres. En revanche, le workflow Terraform reste cohérent.

---

## 8. Infrastructure versionnée avec Git

Un projet Terraform peut être versionné comme un projet logiciel :

```text
Modification de la configuration
        ↓
terraform plan
        ↓
Validation
        ↓
terraform apply
        ↓
Commit Git
```

Si une évolution doit être annulée, on peut revenir à une version antérieure de la configuration puis recalculer les changements à appliquer.

> Le retour à une version Git antérieure ne constitue pas à lui seul un rollback magique de l’infrastructure : Terraform recalculera les changements nécessaires à partir de la configuration, du state et de l’état réel.

## 9. Installation de Terraform sur Ubuntu/Debian

Le support installe Terraform via le dépôt officiel HashiCorp.

### 9.1 Installer les prérequis

```bash
sudo apt-get update
sudo apt-get install -y gnupg software-properties-common curl
```

### 9.2 Installer la clé GPG HashiCorp

```bash
wget -O- https://apt.releases.hashicorp.com/gpg | \
  gpg --dearmor | \
  sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg > /dev/null
```

### 9.3 Vérifier l’empreinte de la clé

```bash
gpg --no-default-keyring \
  --keyring /usr/share/keyrings/hashicorp-archive-keyring.gpg \
  --fingerprint
```

### 9.4 Ajouter le dépôt HashiCorp

```bash
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
```

### 9.5 Mettre à jour l’index des paquets

```bash
sudo apt update
```

### 9.6 Installer Terraform

```bash
sudo apt-get install terraform
```

### 9.7 Vérifier l’installation

```bash
terraform --version
```

Une version Terraform doit être affichée si l’installation est correcte.

## 10. Premiers fichiers Terraform

Terraform accepte principalement :

- le langage **HCL** dans les fichiers `.tf` ;
- une représentation JSON compatible lorsque nécessaire.

Une organisation minimale peut ressembler à :

```text
my-terraform-project/
├── main.tf
├── variables.tf
└── outputs.tf
```

Cette organisation sera enrichie progressivement dans les chapitres suivants.

---

## 11. Workflow Terraform à retenir

Même si les commandes seront détaillées dans le chapitre suivant, le workflow fondamental est :

```text
Écrire la configuration
        ↓
terraform init
        ↓
terraform validate
        ↓
terraform plan
        ↓
terraform apply
        ↓
Infrastructure créée / modifiée
        ↓
terraform destroy   (si nettoyage nécessaire)
```

---

## 12. Points clés à retenir

1. L’IaC transforme l’infrastructure en configuration versionnable et reproductible.
2. Terraform décrit un **état souhaité** plutôt qu’une procédure détaillée.
3. Terraform Core orchestre les changements ; les providers communiquent avec les API.
4. Terraform peut piloter plusieurs plateformes avec un workflow commun.
5. Git apporte traçabilité et collaboration aux configurations d’infrastructure.
6. L’idempotence et la reproductibilité sont des principes centraux de l’IaC.
7. Les fichiers Terraform utilisent principalement HCL et l’extension `.tf`.
