# 192.06 — Terraform : Modules et architecture modulaire

> Sprint 17 — Automatisation  
> Module : Terraform DevOps  
> Durée indicative DataScientest : 1 h  
> Niveau : Normal

## 1. Objectifs pédagogiques

Ce chapitre introduit les **modules Terraform** afin de rendre les configurations plus lisibles, maintenables et réutilisables.

À l’issue de ce chapitre, on doit être capable de :

- définir ce qu’est un module Terraform ;
- distinguer module racine et module enfant ;
- structurer un module avec `main.tf`, `variables.tf` et `outputs.tf` ;
- appeler un module local ;
- utiliser un module publié dans le Terraform Registry ;
- faire communiquer plusieurs modules par variables et outputs ;
- segmenter une architecture AWS en plusieurs blocs fonctionnels.

---

## 2. Pourquoi utiliser des modules ?

Avec le temps, une configuration Terraform peut devenir volumineuse et difficile à maintenir.

Sans modularisation :

```text
Un seul répertoire
    ├── réseau
    ├── instances
    ├── sécurité
    ├── stockage
    ├── bases de données
    └── nombreuses dépendances
```

Avec des modules :

```text
Root Module
   ├── networking
   ├── compute
   ├── storage
   └── database
```

Le support met en avant plusieurs bénéfices :

- maintenabilité ;
- navigation facilitée ;
- cohérence entre environnements ;
- réduction de la dérive ;
- meilleure organisation du code ;
- réutilisabilité.

---

## 3. Terminologie

### 3.1 Module

Un module est un ensemble de fichiers Terraform regroupés dans un même répertoire.

Même une configuration simple contenant quelques fichiers `.tf` constitue déjà un module.

### 3.2 Module racine

Le **root module** est le répertoire depuis lequel les commandes Terraform sont exécutées.

### 3.3 Module enfant

Un module appelé depuis une autre configuration est un **child module**.

### 3.4 Module d’appel

Le module qui appelle un autre module constitue le contexte appelant.

### 3.5 Argument `source`

L’argument `source` indique où Terraform doit trouver le module.

Exemple local :

```hcl
module "networking" {
  source = "./modules/networking"
}
```

Exemple Registry :

```hcl
module "vpc" {
  source = "terraform-aws-modules/vpc/aws"
}
```

---

## 4. Questions à se poser avant de modulariser

Le support insiste sur trois axes.

### Complexité

Le découpage réduit-il réellement la complexité globale ?

### Maintenabilité

Le code reste-t-il facile à comprendre et à faire évoluer ?

### Réutilisabilité

Le module peut-il être utilisé dans plusieurs environnements ou projets sans duplication ?

## 5. Structure recommandée d’un module

Le support propose une structure de base :

```text
module-name/
├── LICENSE
├── README.md
├── main.tf
├── variables.tf
└── outputs.tf
```

Rôle des fichiers :

```text
main.tf
    ↓
Ressources du module

variables.tf
    ↓
Interface d’entrée

outputs.tf
    ↓
Interface de sortie
```

## 7. Module EC2

Arborescence :

```text
modules/ec2/
├── main.tf
├── variables.tf
└── outputs.tf
```

### Data source AMI

```hcl
data "aws_ami" "amazon_linux_2" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm*"]
  }
}
```

### Instance publique

```hcl
resource "aws_instance" "ec2_public" {
  ami                         = data.aws_ami.amazon_linux_2.id
  associate_public_ip_address = true
  instance_type               = "t3.micro"
  key_name                    = var.key_name
  subnet_id                   = var.vpc.public_subnets[0]
  vpc_security_group_ids      = [var.sg_pub_id]
  user_data                   = file("install_wordpress.sh")

  tags = {
    Name = "${var.namespace}-EC2-PUBLIC"
  }
}
```

### Instance privée

```hcl
resource "aws_instance" "ec2_private" {
  ami                         = data.aws_ami.amazon_linux_2.id
  associate_public_ip_address = false
  instance_type               = "t3.micro"
  key_name                    = var.key_name
  subnet_id                   = var.vpc.private_subnets[1]
  vpc_security_group_ids      = [var.sg_priv_id]

  tags = {
    Name = "${var.namespace}-EC2-PRIVATE"
  }
}
```

## 8. Variables du module EC2

Exemple :

```hcl
variable "namespace" {
  type = string
}

variable "vpc" {
  type = any
}

variable "key_name" {
  type = string
}

variable "sg_pub_id" {
  type = any
}

variable "sg_priv_id" {
  type = any
}
```

Ces variables constituent l’interface d’entrée du module.

---

## 9. Outputs du module EC2

```hcl
output "public_ip" {
  value = aws_instance.ec2_public.public_ip
}

output "private_ip" {
  value = aws_instance.ec2_private.private_ip
}
```

Ces outputs rendent les informations disponibles au module appelant.

## 10. Module networking

Arborescence :

```text
modules/networking/
├── main.tf
├── variables.tf
└── outputs.tf
```

### Zones de disponibilité dynamiques

```hcl
data "aws_availability_zones" "available" {}
```

### Module VPC issu du Registry

```hcl
module "vpc" {
  source = "terraform-aws-modules/vpc/aws"

  name            = "${var.namespace}-vpc"
  cidr            = "10.0.0.0/16"
  azs             = data.aws_availability_zones.available.names
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]

  create_database_subnet_group = true
  enable_nat_gateway           = true
  single_nat_gateway           = true
}
```

Le support montre ici qu’un module personnalisé peut lui-même appeler un module tiers.

## 11. Security Group public

Le SG public autorise notamment SSH et HTTP depuis Internet :

```hcl
resource "aws_security_group" "allow_ssh_pub" {
  name        = "${var.namespace}-allow_ssh"
  description = "Autoriser le trafic entrant SSH et HTTP"
  vpc_id      = module.vpc.vpc_id

  ingress {
    description = "SSH depuis Internet"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "HTTP depuis Internet"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

---

## 12. Security Group privé

Le SG privé restreint les accès au réseau interne du VPC :

```hcl
resource "aws_security_group" "allow_ssh_priv" {
  name        = "${var.namespace}-allow_ssh_priv"
  description = "Autoriser le trafic entrant interne"
  vpc_id      = module.vpc.vpc_id

  ingress {
    description = "SSH interne"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/16"]
  }

  ingress {
    description = "HTTP interne"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/16"]
  }
}
```

## 13. Outputs du module networking

```hcl
output "vpc" {
  value = module.vpc
}

output "sg_pub_id" {
  value = aws_security_group.allow_ssh_pub.id
}

output "sg_priv_id" {
  value = aws_security_group.allow_ssh_priv.id
}
```

Ces outputs servent d’interface vers le module EC2.

## 14. Module racine

Le root module appelle les modules enfants :

```hcl
provider "aws" {
  region = "eu-west-3"
}

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

module "networking" {
  source    = "./modules/networking"
  namespace = var.namespace
}

module "ec2" {
  source     = "./modules/ec2"
  namespace  = var.namespace
  vpc        = module.networking.vpc
  sg_pub_id  = module.networking.sg_pub_id
  sg_priv_id = module.networking.sg_priv_id
  key_name   = "Datascientest"
}
```

Ce code montre la communication entre modules :

```text
networking outputs
      ↓
root module
      ↓
ec2 variables
```

## 18. Initialisation et déploiement

```bash
terraform init
terraform apply --auto-approve
```

Terraform télécharge :

- le provider AWS ;
- le module VPC du Terraform Registry.

Nettoyage :

```bash
terraform destroy --auto-approve
```

## 20. Points clés à retenir

1. Toute configuration Terraform est déjà un module.
2. Le répertoire d’exécution est le root module.
3. Un module appelé est un child module.
4. `source` indique l’emplacement du module.
5. Les variables constituent l’interface d’entrée.
6. Les outputs constituent l’interface de sortie.
7. Les modules réduisent la duplication et améliorent la maintenance.
8. Le Terraform Registry fournit des modules réutilisables.
9. Un module peut appeler un autre module.
10. Une architecture complexe peut être segmentée par domaines fonctionnels.
