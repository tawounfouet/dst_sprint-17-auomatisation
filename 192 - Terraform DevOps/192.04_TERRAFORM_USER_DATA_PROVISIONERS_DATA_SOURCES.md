# 192.04 — Terraform : User data, provisioners et data sources

> Sprint 17 — Automatisation  
> Module : Terraform DevOps  
> Durée indicative DataScientest : 1 h  
> Niveau : Normal

## 1. Objectifs pédagogiques

Ce chapitre montre comment enrichir une infrastructure Terraform avec :

- des scripts de démarrage EC2 via `user_data` ;
- des provisioners locaux et distants ;
- des transferts de fichiers ;
- des data sources permettant de récupérer dynamiquement des informations depuis un provider.

À l’issue de ce chapitre, on doit être capable de distinguer les usages de `user_data`, des provisioners et des data sources.

---

## 2. User data sur EC2

Le champ `user_data` d’Amazon EC2 permet d’exécuter des instructions lors du premier démarrage d’une instance.

Terraform peut alimenter ce champ directement.

Exemple inline :

```hcl
resource "aws_instance" "datascientest_instance" {
  ami           = var.image_id
  instance_type = var.type_instance

  user_data = <<EOF
#!/bin/bash
sudo yum update -y
sudo yum install -y httpd
sudo systemctl enable --now httpd
echo "<h1>Datascientest via TERRAFORM</h1>" | sudo tee /var/www/html/index.html
EOF

  monitoring = var.monitoring

  tags = {
    Name = "datascientest"
  }
}
```

Le support précise que ces instructions sont exécutées au lancement de l’instance.

---

## 3. Externaliser le script avec `file()`

Pour éviter de placer un long script dans le HCL, on peut le stocker dans un fichier séparé :

```bash
#!/bin/bash
sudo yum update -y
sudo yum install -y httpd
sudo systemctl enable --now httpd
echo "<h1>Datascientest via TERRAFORM</h1>" | sudo tee /var/www/html/index.html
```

Puis l’injecter :

```hcl
resource "aws_instance" "datascientest_instance" {
  ami           = var.image_id
  instance_type = var.type_instance
  monitoring    = var.monitoring
  user_data     = file("install_apache.sh")

  tags = {
    Name = "datascientest"
  }
}
```

Validation et formatage :

```bash
terraform fmt
terraform validate
```

## 4. Les provisioners Terraform

Les provisioners permettent d’exécuter des actions sur la machine locale ou sur une ressource distante.

Le support les présente notamment comme un moyen de :

- transmettre des fichiers ;
- exécuter des commandes ;
- lancer des outils de configuration comme Ansible, Chef ou Puppet.

Ils sont déclarés dans une ressource.

---

## 5. Objet `self`

Dans un bloc de provisioner, `self` représente la ressource parente.

Exemple :

```hcl
provisioner "local-exec" {
  command = "echo ${self.public_ip} > file.txt"
}
```

Ici, `self.public_ip` désigne l’IP publique de l’instance contenant le provisioner.

---

## 6. Cycle de vie des provisioners

Par défaut, un provisioner s’exécute lors de la création de la ressource.

Le support précise qu’en cas d’échec à la création, la ressource peut être marquée comme incomplètement configurée et planifiée pour recréation lors d’un cycle ultérieur.

### Exécution lors de la destruction

```hcl
provisioner "local-exec" {
  when    = destroy
  command = "echo 'Provisionneur de suppression'"
}
```

Les provisioners définis avec `when = destroy` sont exécutés avant la suppression de la ressource.

---

## 7. Gestion des erreurs

Le méta-argument `on_failure` contrôle le comportement en cas d’erreur.

Valeurs citées :

- `fail` : comportement par défaut ;
- `continue` : ignore l’erreur et poursuit.

Exemple :

```hcl
provisioner "local-exec" {
  command    = "echo IP address is ${self.private_ip}"
  on_failure = continue
}
```

---

## 8. Provisioner `file`

Le provisioner `file` copie un fichier vers une machine distante.

Exemple simplifié :

```hcl
provisioner "file" {
  source      = "configuration.conf"
  destination = "/home/ec2-user/configuration.conf"

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("/chemin/vers/key.pem")
    host        = self.public_ip
  }
}
```

---

## 9. Provisioner `local-exec`

`local-exec` exécute une commande **sur la machine où Terraform s’exécute**.

Exemple :

```hcl
resource "aws_instance" "datascientest_instance" {
  ami           = var.image_id
  instance_type = var.type_instance

  provisioner "local-exec" {
    command = "echo ${self.public_ip} >> public_ip.txt"
  }
}
```

Arguments cités dans le support :

- `command` ;
- `working_dir` ;
- `interpreter` ;
- `environment` ;
- `when`.

---

## 10. Provisioner `remote-exec`

`remote-exec` exécute des commandes sur une ressource distante via SSH ou WinRM.

Exemple :

```hcl
resource "aws_instance" "datascientest_instance" {
  ami           = var.image_id
  instance_type = var.type_instance

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("datascientest_keypair.pem")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo yum update -y",
      "sudo yum install -y httpd",
      "sudo systemctl enable --now httpd"
    ]
  }
}
```

Le support mentionne trois formes :

- `inline` ;
- `script` ;
- `scripts`.

---

## 11. Combiner `file` et `remote-exec`

Exemple pédagogique :

```hcl
provisioner "file" {
  source      = "datascientest-script.sh"
  destination = "/tmp/datascientest-script.sh"
}

provisioner "remote-exec" {
  inline = [
    "chmod +x /tmp/datascientest-script.sh",
    "/tmp/datascientest-script.sh args"
  ]
}
```

Le premier provisioner transfère le script, le second l’exécute.

## 12. Les data sources

Une **data source** lit une information existante via l’API d’un provider au lieu de créer une ressource.

Exemples d’informations pouvant être récupérées :

- AMI disponibles ;
- ressources existantes ;
- propriétés exposées par un fournisseur.

Syntaxe :

```hcl
data "TYPE" "NOM" {
  # filtres
}
```

Puis :

```text
data.TYPE.NOM.ATTRIBUT
```

---

## 13. Exemple AWS : AMI dynamique

Le support cherche à éviter un AMI ID codé en dur, car cet identifiant dépend de la région.

```hcl
data "aws_ami" "datascientest_ami" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*"]
  }
}
```

La ressource EC2 peut alors utiliser :

```hcl
resource "aws_instance" "datascientest_instance" {
  ami           = data.aws_ami.datascientest_ami.id
  instance_type = var.type_instance
}
```

Cette approche rend la configuration moins dépendante d’un identifiant AMI statique.

---

## 14. Différence fondamentale

```text
resource
    ↓
Crée ou gère une ressource

 data source
    ↓
Lit une information existante
```

Et pour l’initialisation d’une VM :

```text
user_data
    ↓
Bootstrap lors du lancement

provisioner
    ↓
Action liée au cycle de vie Terraform
```

---

## 15. Workflow du chapitre

```text
Terraform crée l’EC2
       ↓
AMI récupérée via data source
       ↓
user_data initialise l’instance
       ↓
provisioners éventuels
       ↓
Infrastructure configurée
```

---

## 16. Points clés à retenir

1. `user_data` permet de bootstrapper une instance EC2.
2. La fonction `file()` permet d’externaliser un script.
3. `local-exec` exécute une commande sur la machine Terraform.
4. `remote-exec` exécute des commandes sur une machine distante.
5. Le provisioner `file` copie des fichiers vers une ressource distante.
6. `self` référence la ressource parente dans un provisioner.
7. Une data source lit une information existante depuis le provider.
8. Les data sources permettent notamment d’éviter certains identifiants cloud codés en dur.
